## 자료를 찾는 일이 반복됐다

과거 진단 보고서를 참고할 때 필요한 취약점 사례가 어느 파일에 있는지 찾는 데 시간이 들었다. 파일마다 포함된 취약점 종류가 달라 일일이 열어봐야 했기 때문이다. 문서의 지정된 서식에서 취약점 제목만 추출하는 스크립트를 작성해 필요한 문서를 먼저 고르는 방식으로 바꿨다.

이 작업을 입사 초기에 보고한 뒤, 인원별로 수행한 업무도 파악하고 싶다는 요청을 받았다. 취약점 목록을 모으던 도구를 보고서 수행자와 프로젝트를 집계하는 도구로 확장했다. 이후 연도·월로 조회 기간을 지정하는 기능을 추가했다.

## 출력의 목적이 바뀌면 추출 기준도 바뀌었다

| 단계 | 필요했던 답 | 추출·집계 단위 |
| --- | --- | --- |
| 사례 검색 | 이 취약점이 기록된 문서는 어디에 있는가 | 취약점 제목 → 문서 |
| 업무 현황 | 누가 어떤 보고서·프로젝트에 참여했는가 | 수행자 → 보고서·프로젝트 |
| 기간 조회 | 특정 월에 작성한 자료는 무엇인가 | 기간 → 문서 → 수행자별 집계 |

원본 문서에 같은 수행자나 제목이 반복돼도 보고서 수가 여러 번 증가하지 않아야 한다. 문서 한 개에서 추출한 목록과 문서 간 집계를 분리하고, 사람이 다시 확인할 수 있도록 파일과 추출 항목의 연결을 남기는 방식이 필요했다.

## 공개 재현: 가상 DOCX 세 개로 입력부터 집계까지

회사 문서와 당시 코드는 공개하지 않는다. [독립 예제 다운로드](/examples/report-indexer.zip)는 이 작업의 입력·출력 구조를 설명하려고 새로 작성했다. 생성되는 DOCX는 가상 프로젝트와 수행자만 포함한다.

```text
python -I make_samples.py
python -I report_indexer.py samples --month 2026-10 --output result
python -I verify.py
```

예제는 DOCX의 문단 스타일을 읽어 취약점 제목·수행자·프로젝트를 구분하고, 문서 속성의 수정 날짜로 월을 필터링한다. 기간 기준은 당시 코드와 같다고 주장하지 않으며, 이 예제에서 재현 가능하도록 선택한 규칙이다. 문서별 목록을 JSON과 CSV로 저장하고 수행자별 문서 수·중복 없는 프로젝트 목록을 집계한다.

| 시험 | 기대 결과 |
| --- | --- |
| 같은 수행자가 문서에서 반복됨 | 해당 보고서는 한 번만 집계 |
| 같은 프로젝트의 보고서 두 개 | 보고서 수는 두 개, 프로젝트는 한 개 |
| 다른 달의 보고서 | 지정 월 집계에서 제외 |
| 필요한 문서 메타데이터 누락 | 추정으로 채우지 않고 오류 기록 |

## 업무상 기여

처음에는 내가 자료를 찾는 문제에서 시작했지만, 조직이 필요로 한 집계 결과에 맞춰 목적과 기능을 바꿨다. 업무 자료를 구조화해 반복 조회할 수 있도록 만든 경험이다. 과거 전체 처리 시간과 절감률은 독립적으로 검증한 기록이 없어 수치로 제시하지 않는다.

이 예제의 집계는 업무 현황을 파악하는 자료다. 보고서 수만으로 기여도나 업무 난이도를 판단할 수 없으며, 실제 인사평가를 자동 결정하는 도구로 제공하지 않는다.
