> **이 페이지의 범위**: 공개 블로그에 이미 게시된 보안 분석 및 학습 기록 중 EQST Lab의 AI 보안 연구원 직무와 연결되는 자료를 선별한 안내 페이지다. 아래 문서는 분석 글 또는 학습·점검 방법론이며, 별도로 증적이 제시되지 않은 항목을 실제 취약점 발견, 고객사 진단 성과, AI Red Teaming 수행 또는 PoC 구현 성과로 주장하지 않는다.

## 1. 연구 관점과 지원 직무 연결

이 자료에서 일관되게 사용하는 분석 순서는 **시스템 구조 파악 → 입력과 권한의 신뢰 경계 식별 → 공격 가설 도출 → 검증 조건 설계 → 관찰 사실과 미검증 영역 분리**다.

| EQST Lab 업무와 연결되는 역량 | 이 페이지에서 제시하는 근거 |
| --- | --- |
| Attack Surface 분석 | 웹·API·설치형 클라이언트 등 제공 형태별 입력·권한 경계 분류 |
| 취약점 원인과 공격·방어 기법 분석 | 공개 GitLab CVE의 라우팅·인증·경로 처리 경계 분석 |
| 보안 평가 방법론·기준 | 정적·능동 증적, 비파괴 검증, 판정 기준의 구분 |
| AI Agent·도구 연동 보안에 활용 가능한 기초 | 내부 홉 인증과 사용자 인증의 분리, 기기 간 신뢰 형성, 키 사용 권한 |
| 기술 연구의 반복 가능한 운영 | Scope 기반 공격표면 지도와 가설 검증 프로토콜 |

이 표의 연결은 **기존 보안 연구 관점을 AI 보안 문제에 적용할 수 있다는 확장 가능성**을 설명한다. LLM·LMM·RAG·MCP에 대한 별도의 구현·공격 성공 실적을 뜻하지 않는다.

## 2. 대표 분석: 다중 컴포넌트의 신뢰 경계

### 공개 취약점 분석 — GitLab Path Traversal

[CVE-2026-85706: GitLab Path Traversal을 요청 처리 경계로 이해하기](/portfolio/security/cve-2026-85706-gitlab-path-traversal/)

이 글은 공개 취약점 사례를 `앞단/뒷단 URL 해석 차이 → 내부 홉 검증과 사용자 인증의 구분 → 인증 이전 파일 처리 → 경로 제한 → 오류 기반 정보 노출`이라는 연쇄적인 신뢰 경계 관점으로 분해한다. 특정 제품의 문자열 패턴보다 **서로 다른 컴포넌트가 동일한 입력과 신뢰를 어떻게 다르게 해석하는가**에 초점을 둔다.

**산출물 유형:** 공개 취약점에 대한 구조적 분석 글. 독자적으로 발견한 CVE 또는 직접 검증한 익스플로잇으로 소개하지 않는다.

## 3. 공격면 도출과 평가 기준

### 제공 형태에 따라 점검 범위를 정하는 방법

[웹 서비스 제공 형태별 취약점 점검 관점](/log/security/web-assessment/service-delivery-models-01/)

전통 웹앱, SPA/API, headless API, 위젯, 정적 사이트, 관리 콘솔, 네이티브 앱, WebView, 서비스 간 API, webhook을 분류한다. **서비스 이름이나 공통 체크리스트보다 실제 존재하는 기능과 신뢰 경계를 먼저 확인**하고, 근거가 없는 N/A 판정을 피하는 접근이다.

### 주장과 관찰을 분리하는 평가 방법론

[진술이 아니라 증적으로 판단하는 보안 점검](/log/security/web-assessment/evidence-based-assessment-01/)

`진술 → 검증 가능한 가설 → 정적/능동 증적 → 관찰 → 판정` 흐름을 정리했다. 검증된 양호, 해당 없음(N/A), 자료 부족에 따른 판정불가, 통제 이후의 잔여위험을 구분하며, SBOM과 포크의 변경 범위를 분석할 때도 확인 사실과 추정을 분리한다.

**산출물 유형:** 일반화된 보안 점검 방법론 학습 기록. 특정 고객 환경에 적용해 얻은 실제 결과로 소개하지 않는다.

## 4. 인증·인가·클라이언트 신뢰 모델

### API 요청의 인증과 재전송 방어

[HMAC 요청 인증과 Replay 방어](/log/security/application-architecture/service-design-foundations/hmac-request-authentication-01/)

HMAC의 무결성·주체 인증 범위, timestamp와 nonce의 차이, 다중 인스턴스에서의 재전송 상태 공유, 키 관리와 사용자 인가의 분리를 설명한다. **요청이 유효하게 서명되었다는 사실과 그 작업이 허가되었다는 사실은 다르다**는 관점에 초점을 둔다.

### 기기 간 통신의 최초 신뢰 형성

[LAN P2P 동기화 앱의 신뢰 경계와 페어링 보안](/log/security/web-assessment/lan-p2p-trust-boundaries-01/)

Discovery와 peer 인증의 차이, mTLS·pinning·TOFU의 신뢰 조건, 페어링 재등록, 전송 replay, 수신 endpoint의 별도 입력 검증을 다룬다.

### 키 저장과 사용 권한

[클라이언트 기기 비밀정보와 키 보관 경계](/log/security/web-assessment/device-secret-storage-01/)

OS 보안 저장소, hardware-backed/non-exportable key의 조건, 키 사용 권한, 백업·로그·덤프와 키 생명주기를 정리했다. 비밀키 추출을 막는 것과 키의 부적절한 사용을 막는 것이 별개임을 설명한다.

## 5. 탐지·방어 구조와 연구 워크플로

### 서로 다른 HTTP parser의 해석 정합성

[WAF와 IPS의 차이로 이해하는 웹 방어 구조](/log/security/web-assessment/waf-vs-ips-architecture-01/)

WAF의 HTTP 파싱·정규화·변수 추출과 탐지 모델, IPS와의 역할 차이를 정리했다. 보안 장비의 룰 존재보다 **보호 계층과 백엔드가 동일한 요청을 같은 의미로 해석하는지**가 중요하다는 관점을 제시한다.

### 가설 중심 탐색 프로토콜

[버그바운티 일일 최소 실행 프로토콜](/portfolio/security/bug-bounty-daily-execution-protocol/)

`EXPLORE → VERIFY → REPORT`를 분리하고 Scope, 정상 기준선, 최소 안전 시험, 결과 상태, 다음 탐색 위치를 관리하는 운영 방법을 정리했다. 이 문서는 **탐색 방법을 설계한 산출물**이며 유효 취약점 보고나 보상 실적의 증거는 아니다.

### 추가적인 클라이언트 공격면 학습

[로컬 파일 파싱·렌더링 보안 점검](/log/security/web-assessment/desktop-file-preview-security-01/) · [설치형 클라이언트 무결성·로컬 실행 경계](/log/security/web-assessment/desktop-client-integrity-boundaries-01/) · [메모리 안전 언어와 네이티브 파서의 신뢰 경계](/log/security/web-assessment/memory-safe-native-parsers-01/)

신뢰할 수 없는 파일이 parser·renderer·native bridge로 전달되는 흐름, 코드 서명과 라이브러리 로딩 경계, Rust safe code와 unsafe/FFI 사이의 안전 보장 범위를 학습했다.

## 6. AI 보안 연구로 확장할 질문

다음은 **향후 검증할 연구 질문**이며, 이 페이지에서 완료한 AI 보안 실적으로 주장하지 않는다.

- **LLM/RAG Prompt Injection:** 외부 검색 문서나 검색 결과의 지시문이 사용자·시스템 지시보다 높은 권한을 얻지 못하도록 신뢰 경계를 어떻게 검증할 것인가?
- **AI Agent·MCP Tool Abuse:** 도구 설명과 반환값이 권한 있는 명령으로 승격되지 않도록 어떤 승인·인가·실행 격리 기준을 둘 것인가?
- **Data Leakage 평가:** 검색·도구·모델 응답 경로에서 민감정보가 노출되는지 어떤 재현 가능한 테스트 케이스와 판정 기준으로 확인할 것인가?
- **AI 기반 보안 분석 자동화:** 탐지 후보 생성과 실제 보안 영향 검증을 분리하고, 거짓 양성과 재현성을 어떻게 측정할 것인가?

## 7. 자료의 검증 수준과 공개 범위

이 페이지는 공개 블로그에 게시된 자료를 선별한 **직무 관련성 View**다. 새 실습이나 신규 AI PoC를 수행했다고 주장하지 않는다. 일부 자료는 완결된 공개 취약점 분석 또는 운영 방법론이고, 일부는 실습 전 학습 Log다. 각각의 제목과 본문에서 근거 수준을 확인할 수 있다.

공개 글은 고객·프로젝트·제품을 특정할 수 있는 내부 주소, 비공개 아키텍처, 자격정보, 테스트 계정, 미공개 취약점 세부사항을 포함하지 않는 일반화된 개념 중심으로 연결했다. 채용 담당자가 원문을 확인할 수 있도록 출처 페이지 링크를 제공한다.
