## 두 예제가 다루는 문제는 다르다

설정 파일의 실제 대상을 잘못 읽으면 오탐이 생길 수 있다. 반면 지원하지 않는 장비의 판정을 보류하는 것은 안전한 처리일 수 있다. 이 글은 이 둘을 구분하기 위해 새로 작성한 합성 예제다. 회사·고객 원본 코드를 복제하지 않았다.

[코드·입력·검증 결과 다운로드](/examples/script-review.zip)

## 1. 심볼릭링크 자체와 실제 설정 파일의 권한

설정 파일 경로가 링크일 때 링크 자체의 권한과 대상 파일의 권한은 다를 수 있다. `stat`으로 링크 자체를 보고 판정하는 오류판과 `stat -L`로 대상 파일을 따라가는 수정판을 비교했다.

처음 전달받은 Windows/MSYS 시험에서는 링크가 일반 파일처럼 처리돼 차이가 재현되지 않았다. 이후 Linux(WSL Ubuntu 20.04)의 임시 디렉터리에 가상 설정 파일과 링크를 새로 만들어 확인했다.

| 입력·모드 | 관측 권한 | 출력·종료코드 |
| --- | --- | --- |
| 링크 / 오류판 | 777 | 취약, 1 |
| 같은 링크 / 수정판 | 대상의 640 | 양호, 0 |
| 없는 파일 / 수정판 | 조회 불가 | 수동진단, 2 |

이는 링크 권한 조회의 차이를 보여주는 시험이다. 예제의 권한 기준은 가상 규칙이며 실제 제품의 가이드·소유자·경로 신뢰성까지 검증하지 않는다. [Linux 재검증 출력](/examples/script-review/A_symlink_perm/linux-verification.txt)에 결과를 남겼다.

## 2. 미지원 장비를 전 항목 취약으로 보지 않는다

예제 파서는 정해 둔 가상 문법만 읽는다. 기존 표현 방식은 미지원 입력에 대해 모든 항목을 수동진단으로 나열한다. 개선 표현은 장비 단위로 지원 범위를 확인해야 한다는 사유를 남기고, 항목별 양호·취약 결과는 만들지 않는다.

| 시험 | 기대·관측 결과 |
| --- | --- |
| 지원·미지원 입력 / 기존 표현 | 미지원 항목들이 수동진단으로 나열, 종료코드 0 |
| 같은 입력 / 개선 표현 | 장비 단위 보류·항목 결과 없음, 종료코드 2 |
| 파일 읽기 실패 | 수집 실패, 종료코드 2 |

**미지원 처리가 기존 결함이었다고 주장하는 예제는 아니다.** 지원 범위를 더 명확히 드러내는 새 설계다. 코드의 문법 키워드 검사도 실제 제품 식별기가 아니며, 유효한 설정에서도 키워드가 없으면 수동 확인이 필요하다.

항목 이름은 실제 점검 기준과 혼동하지 않도록 `ITEM-01` 등 가상 식별자를 사용했다. [현재 코드의 재검증 결과](/examples/script-review/B_unsupported_device/verification.json)에서 입력과 출력을 대조할 수 있다.
