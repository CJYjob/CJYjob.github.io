## 두 번 읽는 것만으로 독립 검증이 되지는 않았다

분석자가 내린 판정을 검증자가 먼저 보면 같은 결론에 영향을 받을 수 있었다. 그래서 원본 증적과 판정 기준을 먼저 전달하고, 검증자의 자체 판단이 나온 뒤 분석 결과와 비교하는 순서를 뒀다. 이 글은 [대표 글](/portfolio/security/ai-assessment-workflow/)의 역할과 통제를 실행 단위로 풀어 설명한다.

| 역할 | 입력 | 출력·넘김 조건 |
| --- | --- | --- |
| 기획 | 대상·기준·제약 | 증적·출력·시험 계획 |
| 개발 | 계획과 결함 목록 | 코드·실행 안내·항목 매핑 |
| QA | 계획·코드·시험 입력 | 결함 근거 또는 검증 결과; 수정은 개발로 반환 |
| 분석 | 원본 결과·기준 | 항목별 판정과 증적 위치 |
| 독립 재판정 | 라벨을 뺀 항목·증적 위치·원본 | 먼저 자체 판단, 이후 분석 결과와 대조 |
| 보고·기록 | 확인된 결과와 차이 | 산출물과 다음 작업에서 참고할 오류 기록 |

## 규칙이 존재하는 것과 효과가 확인되는 것은 다르다

| 통제 | 정의한 동작 | 실제 기록에서 확인된 범위 |
| --- | --- | --- |
| 재작업 상한 | 개발·검증 최대 3회 후 사람에게 확인 요청 | 결함 재작업은 1회 뒤 통과. 상한 분기 미검증 |
| 정적 검사기 | 금지 패턴·출력 표식 검사 | 기록은 모두 PASS. 실제 결함 발견은 QA의 시험 실행 |
| 쓰기 가드 | 지정 경로에서 위험 패턴 검사 | 등록과 경로 제한은 확인. 실제 쓰기 차단 기록 미확인 |
| 로그 점검 훅 | 산출물 대비 로그 누락 시 종료를 한 번 보류 | 발동 표식 확인. 로그 내용의 정확성까지 검증하지 않음 |
| 라벨 없는 재판정 | 원본 판단 후 결론 비교 | 일부 실행의 핸드오프·재판정 순서 확인 |

쓰기 가드는 문자열과 경로를 기준으로 동작했다. 검사 경로 밖에 코드를 쓰거나 검사에서 제외한 확장자에 내용이 들어가면 같은 통제가 적용되지 않는다. 문서에 “위험 명령 금지”라고 적는 것과 실행 권한을 제한하는 것은 별도 조치다.

## 다음 구현에서 확인할 조건

통제를 평가하려면 이름과 지시문보다 차단돼야 하는 동작을 직접 시험해야 한다. 예를 들어 허용 경로와 경로 밖, 금지 명령이 주석에만 있는 경우, 파싱 실패, 로그는 있지만 비어 있는 경우를 나눠 기대 동작을 정한다. 이 항목은 새 통제의 수용 시험 제안이며 과거 실행 성과가 아니다.

독립 재판정도 입력에서 라벨만 뺐는지와 검증자가 원본보다 분석 결론을 먼저 읽었는지를 따로 확인해야 한다. 결과가 같다는 이유만으로 독립적인 검증이 수행됐다고 판단하지 않는다.
