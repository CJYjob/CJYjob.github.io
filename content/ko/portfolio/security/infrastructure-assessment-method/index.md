## 점검을 실행하는 것과 결과를 사용할 수 있는 것은 달랐다

서버·DBMS·네트워크·보안 장비와 클라우드는 같은 방법으로 증적을 수집할 수 없다. 허용된 계정으로 스크립트를 실행하거나, 전달받은 장비 설정을 분석하거나, 운영 항목을 인터뷰로 확인했다. 중요한 것은 각 결과가 **어떤 자산에서 어떤 권한으로 얻은 값인지** 연결하는 일이었다.

이 글은 [ISMS 점검 기록](/log/security/infrastructure-assessment/isms-assessment-scope-evidence-01/)과 [증적 중심 점검 학습](/log/security/web-assessment/evidence-based-assessment-01/)을 바탕으로 재사용 가능한 확인 순서를 정리한 산출물이다. 고객 환경의 전체 구성이나 실제 결함 현황은 포함하지 않는다.

## 1. 대상과 수집 경로를 먼저 대응시킨다

| 대상 | 가능한 수집 경로 | 결과를 쓰기 전 확인 |
| --- | --- | --- |
| 서버·DBMS | 승인된 계정과 점검 스크립트 | 권한, 실제 설정 경로, 조회 성공 여부 |
| 네트워크 장비 | 담당자가 제공한 설정 | 장비 종류·설정 시점·자산 대응 |
| 보안 장비 | 설정 자료와 인터뷰 | 답변을 뒷받침하는 증적과 해당 자산 |
| 클라우드·컨테이너 | 읽기 전용 API·설정 조회 | 계정 범위, 호스트·프로그램·이미지 계층 |

컨테이너 안의 프로그램은 호스트에서 찾는 경로와 다를 수 있었다. 실제 환경에서 수집 경로가 맞지 않는 문제를 확인한 뒤 프로그램 설정을 가져와 판단하도록 방식을 바꿨다. 값이 없다는 결과를 프로그램이 없다는 결론으로 바로 바꾸지 않았다.

## 2. 파일 이름만으로 자산을 확정하지 않는다

장비 설정의 이름과 자산대장의 이름이 다르면 결과를 다른 자산에 붙일 수 있다. 확인한 식별 정보와 대장을 대조하고, 하나의 결과가 여러 자산 기록과 연결되는 경우 대응 관계를 따로 남겼다. 기술 판정을 하기 전에 입력과 대상의 관계를 검증해야 했다.

```text
가상 자산: LAB-01
수집 입력: 설정 파일 A
수집 조건: 읽기 계정 / 승인된 설정 조회
확인 상태: 설정 조회 성공, 대상 식별 일치
판정 근거: 기준 항목과 설정 위치
미확인 범위: 인터뷰 또는 추가 증적이 필요한 항목
```

위 형식은 실제 자산대장의 치환본이 아닌 합성 기록 예시다.

## 3. 판정 전에 수집 상태를 확인한다

자동 점검 결과에는 값과 안내 문구가 함께 들어갈 수 있다. 조회 실패, 빈 파일, 미지원 제품, 해당 기능 없음은 서로 다른 상태다. 이 중 무엇을 관찰했는지 먼저 기록하고, 필요한 증적을 확보하지 못하면 확인이 필요한 상태로 남긴다.

위험평가에서는 자산 가치·취약점 위험도·현재 통제를 검토해 위험 수용과 감소를 구분하고, 감소 항목의 조치 시기를 정리했다. 자동 계산된 보고서도 자산별 참조와 입력·출력 대응을 확인한 뒤 사용해야 한다.

## 현업 재사용 확인표

- 대상의 제품·버전과 점검 범위가 일치하는가?
- 실행 계정에 필요한 조회 권한이 있는가?
- 수집 실패·미지원·해당 없음이 구분되는가?
- 결과 파일과 자산의 대응을 확인했는가?
- 빈 입력과 인코딩 차이를 시험했는가?
- 판정에 사용한 원본 설정과 기준 위치가 남는가?
- 검증한 버전과 실제 실행한 파일이 같은가?
- 완료된 조치는 같은 조건으로 재검증했는가?
