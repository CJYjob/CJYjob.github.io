## 어떤 일을 했나

헌팅마스터 교육에서 퍼징을 접한 뒤, 모의해킹 교육에서 만난 동료들과 자율 연구를 시작했다. AI 서비스를 오케스트레이터로 활용해 오픈소스를 대상으로 입력 생성과 크래시 분석을 진행했다. libConfuse에서 확인한 크래시 3건은 관리자에게 비공개 보안 보고서로 전달했다. 보안 보고 채널이 없었기 때문에 먼저 채널 개설을 요청했고, 관리자가 기능을 연 뒤 보고서를 제출했다.

이것은 크래시 보고 경험이다. 취약점 인정, 수정 반영, CVE 부여는 별개의 확인이 필요하므로 발견 성과로 합쳐 적지 않는다. 미공개 입력과 원인·재현 단계는 이 페이지에 포함하지 않는다.

## 반복 실행과 연구 판단의 역할을 나눴다

퍼징은 입력을 반복 실행하고 실패를 수집하는 일이다. AI가 매 실행을 지휘하게 하면 비용과 상태 관리 부담이 커진다. 개인 연구 플랫폼에서는 반복 실행·통계 수집·자원 배정을 결정적인 코드로 처리하고, AI는 하네스 검토나 수집된 결과의 분석·개선안 작성에 사용하는 방향을 정했다.

| 단계 | 확인할 질문 | 관리할 근거 |
| --- | --- | --- |
| 대상 선정 | 실제 구현이 다른 대상인가, 로컬에서 시험할 수 있는가 | 대상 버전·소스 리비전·범위 |
| 하네스 준비 | 원하는 API까지 입력이 전달되는가 | 빌드·계측·smoke test |
| 반복 실행 | 실행 중인지, 정지했는지, 결과가 최신인지 | 워커 상태·heartbeat·통계 |
| 크래시 분석 | 같은 원인인지, 재현 가능한지 | 환경과 버전이 고정된 재현 기록 |
| 개선안 평가 | 입력이나 하네스를 바꾼 것이 실제로 나은가 | 동일 조건 비교·승격 여부 |

AI가 만든 제안을 바로 운영 설정으로 올리지 않도록 비교 결과와 완료 조건을 별도로 둔다. 로컬 소스에는 워커 예산, 실행 스케줄, 하네스 검증과 비교 실험을 위한 모듈이 있다. 설계 문서의 기능 전체가 구현됐다는 의미는 아니다.

## 제안이 좋아 보여도 비교에서 나쁘면 채택하지 않았다

개인 연구 기록에는 후보 실행 방식과 기준선을 여러 seed로 비교하고, 후보의 coverage 지표가 기준선보다 낮아 승격을 차단한 사례가 남아 있다. 이 결과는 자동화가 항상 성능을 올린다는 주장을 뒷받침하지 않는다. 개선안의 채택 조건을 실행 결과와 연결했다는 점이 중요하다.

현재 공개 자료는 아래의 합성 실험으로 그 판단 원칙을 재현한다. 실제 연구 대상의 입력·크래시·성능 수치는 사용하지 않는다.

## 내가 맡은 부분

연구 목표와 범위, 데이터 취급, 중단·승인 조건을 정하고 AI와 도구를 이용해 환경과 실행 흐름을 구성했다. 코드와 문서 작성에는 AI를 활용했다. 크래시를 검토하고 보안 보고 채널을 요청해 제보한 과정은 연구 활동의 일부다. 독자적인 AI 모델 학습이나 LLM·Agent 자체의 공격면 분석 경험으로 소개하지 않는다.

현재의 과제는 실행량보다 도달 경로·재현성·중복 원인 분석을 기준으로 연구 품질을 확인하는 것이다. 운영 명령이나 제보 상세를 공개하는 대신, 이 페이지에서는 실행과 판단을 분리한 구조와 공개 가능한 검증 원칙을 남긴다.
