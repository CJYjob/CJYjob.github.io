## 크래시 수만 늘었다고 개선이라고 할 수 있을까

실행 조건이 다른 결과를 비교하거나 필수 지표가 빠진 결과를 받아들이면 개선안을 잘못 채택할 수 있다. [개인 퍼징 연구](/portfolio/security/oss-fuzzing-orchestration/)에서는 반복 실행과 승격 판단을 도구로 확인하는 방향을 정했다. 이 글의 코드는 그 원칙을 설명하는 **새 합성 예제**다.

고객사 정보와 미공개 취약점 입력을 사용하지 않는다. 실제 프로젝트의 비교 게이트 전체를 복제한 것도 아니다. 실행 시간과 리비전이 같고, 정해 둔 지표가 모두 존재할 때만 coverage 중앙값을 비교하는 최소 규칙이다.

| 합성 사례 | 기대 결과 |
| --- | --- |
| 소스 리비전이 다름 | 비교 거부 |
| 측정값 누락 | 판단 보류 |
| 같은 조건에서 후보 coverage가 낮음 | 승격 차단 |
| 같은 조건에서 후보 coverage가 높음 | 예제 규칙상 통과 |

[코드와 시험 자료 다운로드](/examples/promotion-gate.zip) 후 `python -I gate.py`로 실행한다. 이 시험을 통과해도 실제 퍼징 품질을 증명하지 않는다. 실무 연구에서는 seed·자원·시간·안정성·목표 경로 도달과 원인 중복을 함께 검토해야 한다.

이 예제의 목적은 AI 제안을 자동으로 신뢰하는 대신, 사전에 정한 비교 조건을 코드로 확인하고 부족한 자료를 보류 상태로 드러내는 것이다.
