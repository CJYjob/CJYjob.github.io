## 목적

버그바운티를 **취약점을 찾았을 때만 성공하는 활동**이 아니라, 매일 정해진 탐색 사이클을 닫으면 완료되는 실행 시스템으로 운영한다.

핵심 목표는 다음 네 가지다.

1. 사용자가 매일 프로그램과 점검 위치를 처음부터 고민하지 않게 한다.
2. 취약점 발견 여부와 관계없이 최소 탐색 단위가 항상 종료될 수 있게 한다.
3. 반복 활동이 프로그램별 공격표면 지도와 탐색 이력으로 누적되게 한다.
4. 실제 보상 가능성과 정보보안 실무 역량 축적을 함께 추적한다.

실제 테스트는 항상 해당 플랫폼과 개별 프로그램의 최신 Scope·정책·허용 범위를 우선한다. 플랫폼 일반 규칙보다 개별 프로그램 규칙이 더 구체적이면 개별 프로그램 규칙을 따른다.

## 1. 기본 상태 머신

버그바운티 활동은 세 종류의 닫히는 단위로 분리한다.

```text
EXPLORE
대상 결정
→ Scope/정책 확인
→ 공격표면 노드 1개 선택
→ 최소 안전 테스트
→ 결과 분류
→ 공격표면 지도 갱신
→ 다음 탐색 포인터 결정
→ 종료

VERIFY
후보 발견
→ Scope/정책 재확인
→ 최소 안전 재현
→ 증거 정리
→ 영향 분석
→ 중복 가능성 확인
→ 후보 상태 결정
→ 종료

REPORT
검증된 후보
→ 보고서 작성
→ 재현 절차·영향·증거 점검
→ 제출 적합성 판단
→ 제출 또는 보류
→ 결과 추적 상태 생성
→ 종료
```

일반 탐색과 취약점 후보 검증·보고는 서로 다른 단위다. `EXPLORE` 도중 후보가 생겨도 그 자리에서 과도하게 검증하지 않고 다음 상태로 넘긴다.

## 2. 버그바운티 최소 1단위의 정확한 정의

기본 1단위는 **`EXPLORE-1`** 이다.

완료 조건은 취약점 발견이 아니라 다음 일곱 조건의 충족이다.

1. 오늘 사용할 프로그램이 정해졌다.
2. 해당 프로그램의 현재 Scope·정책을 확인했다.
3. 공격표면 지도에서 기능 또는 표면 1개와 테스트 관점 1개를 선택했다.
4. 정상 동작 기준을 한 번 확인했다.
5. 선택한 테스트 관점에 맞는 안전한 변형을 최소 1회 수행했다.
6. 결과를 `정상 / 이상 관찰 / 후보` 중 하나로 분류했다.
7. 현재 노드 상태와 다음 탐색 위치를 기록했다.

이 일곱 조건이 끝나면 **취약점이 없어도 1단위 완료**다.

기본 시간은 반복 운영 시 **20~30분**을 예상한다.

- Scope·정책 재확인: 2~5분
- 노드 선택: 1~3분
- 실제 점검: 10~15분
- 결과 정리·다음 포인터: 3~7분

새 프로그램을 처음 등록하는 날은 프로그램 구조와 정책을 읽어야 하므로 **30~45분**까지 허용한다. 그 이후에는 기존 상태를 이어받는다.

시간이 부족해도 테스트 자체를 생략한 단순 자료 열람은 `EXPLORE-1` 완료로 계산하지 않는다.

## 3. 프로그램 선정 — 하드 게이트

HackerOne과 Find the Gap의 프로그램 후보는 먼저 아래 조건을 모두 통과해야 한다.

1. 현재 참여 가능한 활성 프로그램이다.
2. 실제 보상이 존재하거나 보상 가능성이 명확하다.
3. 사용자가 해당 프로그램에 참여할 자격과 접근 권한을 갖는다.
4. Scope가 충분히 명확하다.
5. 오늘 수행하려는 테스트 유형이 정책상 허용된다.
6. 실제 서비스에 불필요한 피해를 주지 않고 검증할 수 있다.
7. 사용자 현재 역량과 도구로 최소 탐색 단위를 수행할 수 있다.

하드 게이트 하나라도 실패하면 탐색 대상에서 제외한다.

현재 수입 필요성을 고려하여 **연습용 CTF보다 실제 보상 프로그램을 우선**한다. 단, 실제 프로그램에 적용할 수 없는 공격기법은 테스트베드 학습으로만 전환한다.

## 4. HackerOne 프로그램 선정 기준

HackerOne에서는 공식 Opportunity/Directory와 각 Security Page의 정보를 기준으로 선정한다.

우선순위는 다음과 같다.

### 1순위 — 참여 가능성과 정책 명확성

- Active Program
- Offers bounties
- 명확한 in-scope asset
- 명확한 Scope Exclusions
- 테스트 요구사항과 금지사항 확인 가능
- 사용자 계정이 제출 요구조건을 충족

### 2순위 — 보상과 프로그램 건강도

Security Page에서 확인 가능한 경우 다음을 본다.

- 최근 90일 bounty 지급 여부
- 평균 bounty
- 최고 bounty 범위
- 최근 보고 처리 활동
- response efficiency
- 평균 first response / triage / bounty 시간

### 3순위 — 사용자 적합성

현재 주력인 웹·API 점검과 연결되는 자산을 우선한다.

- 웹 애플리케이션
- API
- 인증·권한이 있는 사용자 기능
- 상태 변경이 발생하는 비즈니스 기능
- 파일·외부 연동·사용자 입력 처리 기능

### 4순위 — 경쟁 대비 탐색 가치

동점이면 다음 순서로 우선한다.

1. 참여 중인 private program
2. 새로 추가되거나 최근 변경된 자산이 있는 프로그램
3. 기존에 공격표면 지도가 누적되어 있어 바로 다음 탐색이 가능한 프로그램
4. public program

Private program은 참여자가 제한되므로 기회가 될 수 있지만, 비공개 프로그램명·정책·취약점 내용은 공개 저장소에 기록하지 않는다.

## 5. Find the Gap 프로그램 선정 기준

Find the Gap도 동일한 하드 게이트를 적용하되, 실제 참여 화면에 표시되는 개별 프로그램 정보를 우선한다.

다음 순서로 평가한다.

1. 현재 참여 승인 상태
2. 보상 조건과 금액
3. Scope와 제외 영역
4. 테스트에 필요한 VPN·VDI 등 접속 조건
5. 허용·금지 테스트 방식
6. 보고 절차와 중복 처리 기준
7. 현재 사용자 역량과 서비스 구조의 적합성

Find the Gap은 private 또는 제한형 프로그램이 존재하므로, 로그인 뒤에만 보이는 정보는 외부 검색 결과로 추정하지 않는다. 필요한 프로그램 규칙은 사용자가 접근 가능한 실제 프로그램 페이지를 기준으로 한다.

## 6. 프로그램 운영 수 — Primary + Reserve

동시에 깊게 추적하는 프로그램은 기본적으로 두 개만 둔다.

- `PRIMARY`: 현재 연속 탐색 중인 프로그램
- `RESERVE`: PRIMARY 전환 시 바로 이어갈 프로그램

후보 프로그램 목록 자체는 여러 개일 수 있지만, 사용자가 매일 선택하지 않도록 코치가 Primary와 Reserve를 관리한다.

새로운 취약점 후보가 생기면 해당 프로그램은 자동으로 최우선 상태가 된다.

## 7. 한 프로그램을 계속 볼지 전환할지 결정하는 규칙

한 프로그램은 최소한 **서로 다른 노드 3개**를 닫기 전에는 단순히 "안 나왔다"는 이유로 버리지 않는다.

다음 조건 중 하나라도 만족하면 계속한다.

- 아직 확인하지 않은 우선순위 높은 기능이 있다.
- 기존 기능에 확인하지 않은 테스트 관점이 있다.
- 최근 서비스·정책·Scope 변경이 있다.
- 직무 브리핑의 `/take` 항목이 현재 자산과 직접 연결된다.
- 이상 관찰 또는 후보 상태가 있다.
- 이전 탐색에서 새로운 기능·흐름·신뢰경계가 발견됐다.

다음 조건을 모두 만족하면 프로그램 전환을 검토한다.

1. 우선순위 높은 노드가 1차로 모두 확인됐다.
2. 최근 5개 `EXPLORE` 단위에서 후보가 없었다.
3. 최근 3개 단위에서 새로운 공격표면·동작 구조도 거의 추가되지 않았다.
4. 동일 프로그램에서 남은 노드의 기대가 Reserve보다 낮다.

전환된 프로그램은 폐기하지 않고 `COOLDOWN` 상태로 둔다. 이후 다음 트리거가 생기면 다시 활성화한다.

- Scope 또는 서비스 변경
- 신규 기능 발견
- 브리핑의 새로운 관련 기법
- 프로그램 공지
- 후보 후속 요청

## 8. 프로그램별 공격표면 지도

단순 시간 기록 대신 다음 계층으로 관리한다.

```text
프로그램
└─ 자산
   └─ 기능/공격표면
      └─ 테스트 관점
         ├─ 상태
         ├─ 관찰 결과
         ├─ 마지막 확인 조건
         ├─ 재확인 트리거
         └─ 다음 위치
```

### 자산 예시 분류

- Web
- API
- Mobile
- 기타 프로그램이 명시한 자산

### 기능/공격표면 예시 분류

- 로그인·세션
- 가입·계정복구
- 사용자 프로필
- 역할·권한
- 객체 조회·수정
- 검색·필터·입력
- 파일 업로드·다운로드
- 외부 URL·연동
- 알림·초대·공유
- 관리자·운영 기능
- 결제·주문·쿠폰 등 상태 전이
- API 전용 기능

### 테스트 관점 예시

- 인증 경계
- 권한·소유권 경계
- 입력 해석
- 상태 전이와 업무 규칙
- 클라이언트·서버 신뢰경계
- 외부 리소스 처리
- 파일·콘텐츠 처리
- 정보 노출
- 반복·자동화 제한
- 세션·토큰 수명주기

취약점 이름부터 정하고 찾는 방식보다 **기능이 어떤 보안 가정을 가지고 있는지 확인하는 방식**을 우선한다.

## 9. 공격표면 노드 상태

각 `기능 × 테스트 관점` 조합은 다음 상태 중 하나를 가진다.

- `READY`: 아직 확인하지 않음
- `TESTED_EXPECTED`: 확인했고 예상 범위의 동작
- `TESTED_ANOMALY`: 이상하지만 보안 영향은 미확정
- `REVIEW_LATER`: 정보나 조건이 부족해 재확인 필요
- `EXCLUDED`: Scope·정책·기술 조건상 현재 제외
- `CANDIDATE_LOCKED`: 취약점 후보 검증으로 이동

`TESTED_EXPECTED` 노드는 이유 없이 다시 반복하지 않는다.

재탐색은 다음 트리거가 있을 때만 허용한다.

- 서비스 동작 또는 버전 변화
- Scope·정책 변화
- 새 기능 또는 새 입력 경로 발견
- 이전 테스트의 조건 누락 발견
- 직무 브리핑에서 기존과 다른 관점이 유입
- 프로그램이 재검증을 요청

## 10. Scope·정책 확인 절차

매 `EXPLORE`와 `VERIFY` 시작 전에 다음을 확인한다.

1. 프로그램이 현재 활성 상태인지
2. 오늘 사용할 자산이 in-scope인지
3. 해당 자산이 bounty eligible인지
4. 제외된 취약점 유형이 무엇인지
5. 금지된 테스트 방식이 무엇인지
6. 자동화·요청 빈도 제한이 있는지
7. 테스트 계정·식별 헤더·VPN·VDI 등 필수 조건이 있는지
8. 개인정보·타인 데이터·운영 서비스 영향에 관한 제한이 있는지
9. 보고·공개·중복 관련 규칙이 무엇인지

정책이 모호하면 추정해서 진행하지 않는다. 프로그램에 확인하거나 다른 노드로 이동한다.

HackerOne의 Safe Harbor가 표시되어 있어도 그것이 Scope를 넓히는 것은 아니다. **Safe Harbor와 Scope는 별도로 확인**한다.

DoS·DDoS, 과도한 요청, 사회공학, 사용자·관리자에게 불필요한 알림을 발생시키는 테스트 등은 프로그램이 명시적으로 허용하지 않으면 수행하지 않는다.

## 11. 실제 테스트의 최소 범위

한 `EXPLORE-1`에서 테스트 관점은 하나만 잡는다.

기본 패턴은 다음과 같다.

1. 정상 사용자 흐름을 한 번 확인한다.
2. 현재 기능의 보안 가정 하나를 명시한다.
3. 그 가정과 관련된 입력·상태·권한 조건을 하나만 바꾼다.
4. 정상 기준과 결과 차이를 본다.
5. 필요한 경우 같은 관점에서 안전한 변형을 1~2회 더 확인한다.
6. 예상 동작이면 닫고, 이상하면 상태를 전환한다.

요청 수를 늘리는 것이 목표가 아니다. **하나의 가설을 안전하게 닫는 것**이 목표다.

다른 사용자의 실제 데이터 접근, 서비스 중단, 대량 요청, 실제 금전·메시지·외부 행위 발생 등 불필요한 영향이 필요해지는 순간 테스트를 멈춘다.

## 12. 취약점을 발견하지 못했을 때의 정상 종료조건

다음이 모두 끝났으면 정상 완료다.

- Scope 확인 완료
- 공격표면 노드 선택 완료
- 정상 기준 확인 완료
- 테스트 관점 1개 적용 완료
- 의미 있는 차이 없음 또는 방어 동작 확인
- 노드를 `TESTED_EXPECTED`로 변경
- 다음 `READY` 노드 지정

종료 기록은 "30분 봄 / 취약점 없음"이 아니라 다음 구조로 남긴다.

```text
프로그램: P1
자산: A1
기능: 계정복구
관점: 권한·소유권 경계
결과: TESTED_EXPECTED
관찰: 기대한 소유권 검증 동작 확인
다음: 동일 자산의 세션 수명주기
```

## 13. 의심스러운 현상을 발견했을 때

보안 영향은 아직 확실하지 않지만 예상과 다른 동작이 보이면 `TESTED_ANOMALY`로 전환한다.

이때 일반 탐색은 즉시 닫는다.

다음 행동은 추가 공격이 아니라 다음 네 가지다.

1. 어떤 정상 기준과 달랐는지 기록
2. 재현에 필요한 최소 조건 기록
3. Scope와 정책을 다시 확인
4. 다음 단위를 `VERIFY`로 예약

그 자리에서 영향도를 키우려고 다른 사용자·다른 데이터·운영 환경으로 확장하지 않는다.

## 14. 취약점 후보 검증 프로토콜

`VERIFY-1`은 다음 순서로 수행한다.

```text
후보 발견
→ Scope/정책 재확인
→ 최소 안전 재현
→ 증거 정리
→ 영향 분석
→ 중복 가능성 검토
→ 보고 적합성 판정
```

### 검증 통과 조건

다음 세 가지가 모두 있어야 실제 보고 후보로 승격한다.

1. **재현성:** 동일한 최소 조건에서 다시 관찰된다.
2. **보안 속성 위반:** 인증·권한·기밀성·무결성·가용성·업무 규칙 중 무엇이 깨지는지 설명할 수 있다.
3. **안전한 영향 근거:** 다른 사용자나 서비스에 불필요한 피해를 주지 않고 영향의 존재를 보여줄 수 있다.

보안 영향을 증명하려면 타인 데이터 열람, 파괴적 동작, 과도한 요청, 실제 금전 손실 등이 필요하다면 그 지점에서 멈춘다. 가능한 최소 증거까지만 수집하고 프로그램에 문의하거나 그대로 보고한다.

## 15. 중복 가능성 검토

후보 검증이 끝나면 제출 전에 중복 가능성을 점검한다.

- 프로그램의 공개된 known issue
- 프로그램이 제공하는 공지·FAQ
- 공개가 허용된 HackerOne Hacktivity·기존 disclosure
- 프로그램이 제공한 중복 관련 안내

비공개 프로그램의 내부 정보를 공개 검색으로 유추하거나 외부에 노출하지 않는다.

중복 가능성이 있다는 이유만으로 과도하게 추가 테스트하지 않는다. 동일 root cause로 보이면 보고서에서 그 관계를 명확히 설명한다.

## 16. 보고 프로토콜

검증된 후보는 `REPORT-1`로 전환한다.

보고서에는 최소한 다음을 포함한다.

1. 취약점이 무엇인지
2. 영향받는 in-scope 자산
3. 최소 재현 절차
4. 실제 관찰 결과
5. 기대 동작과 실제 동작 차이
6. 보안 영향
7. 필요한 증거
8. Scope·정책 준수 여부

HackerOne에서는 제출 전에 Scope와 중복 여부를 다시 확인하고, 재현 절차와 영향이 명확한 보고서를 우선한다.

제출 상태는 다음처럼 추적한다.

- `DRAFT`
- `SUBMITTED`
- `NEEDS_INFO`
- `VALID`
- `DUPLICATE`
- `INFORMATIVE`
- `N/A_OR_INVALID`
- `RESOLVED`
- `BOUNTY_PAID`

플랫폼마다 실제 상태명은 다를 수 있으므로 `platform_status`와 위 정규화 상태를 별도로 기록한다.

## 17. 동일 영역을 의미 없이 반복하지 않는 규칙

각 노드는 `자산 × 기능 × 테스트 관점`의 고유 조합으로 본다.

코치는 새 단위를 지정하기 전에 반드시 기존 지도를 확인한다.

다음 조건이 없으면 `TESTED_EXPECTED` 노드를 다시 지정하지 않는다.

- 새 입력 경로
- 새 역할 또는 계정 조건
- 서비스 변경
- 정책 변경
- 새 브리핑 기법
- 이전 테스트 불완전
- 프로그램 재검증 요청

특정 접근 방식이 반복해서 성과가 없을 때는 다음처럼 처리한다.

- 같은 프로그램·기능군에서 10회 이상 사용했는데 후보도 없고 새로운 구조적 학습도 거의 없으면 우선순위를 낮춘다.
- 동일 유형의 제출이 `N/A / Informative`로 반복되면 해당 판단 로직을 재검토하기 전까지 같은 방식의 신규 제출을 제한한다.
- `Duplicate`가 반복되면 더 빠른 탐색보다 **다른 기능·다른 신뢰경계·다른 서비스 변화** 쪽으로 전환한다.

## 18. 직무 브리핑 `/take` 연동

매일 04:00 KST 직무 브리핑의 `/take ITEM_ID`는 곧바로 실제 공격 지시가 아니다.

`/take` 된 버그바운티 관련 항목은 먼저 `BRIEFING_HYPOTHESIS` 상태가 된다.

적용 절차:

1. 항목이 설명하는 핵심 보안 가정을 추출한다.
2. 어떤 자산·기능 조건에서만 적용 가능한지 정리한다.
3. 현재 PRIMARY 프로그램에 해당 조건이 있는지 본다.
4. 해당 자산이 Scope 안인지 확인한다.
5. 필요한 테스트 방식이 정책상 허용되는지 확인한다.
6. 안전하게 검증 가능한 경우에만 새 테스트 관점으로 지도에 추가한다.

다음 중 하나라도 실패하면 실제 서비스에 적용하지 않는다.

- 자산이 out-of-scope
- 취약점 유형이 제외됨
- 필요한 테스트가 금지됨
- 실제 사용자·운영 서비스에 불필요한 영향이 예상됨
- 전제 조건이 현재 서비스와 맞지 않음

적용하지 못한 `/take` 항목은 다음 중 하나로 닫는다.

- `TESTBED_ONLY`: 테스트베드 학습으로 전환
- `FUTURE_SURFACE`: 조건이 맞는 프로그램이 나타날 때 재사용
- `NOT_APPLICABLE_POLICY`
- `NOT_APPLICABLE_SURFACE`

실제 탐색에 사용한 뒤에는 다음 중 하나로 결과를 남긴다.

- `APPLIED_EXPECTED`
- `APPLIED_NEW_SURFACE`
- `APPLIED_ANOMALY`
- `APPLIED_CANDIDATE`

이 결과는 다음 직무 브리핑 선별과 보안 학습 소재 판단에 피드백으로 사용한다.

## 19. 사용자가 수행 후 코치에게 보내는 최소 정보

코치가 오늘 대상과 노드를 이미 지정했으므로 사용자는 다음만 보내면 된다.

```text
결과: 정상 | 이상 | 후보
관찰: 한 줄
```

계획과 다르게 진행한 것이 있으면 한 줄만 추가한다.

```text
예외: 계획과 달랐던 점
```

사용자가 별도로 프로그램명·기능명·테스트 관점을 매번 반복 입력할 필요는 없다.

## 20. 코치가 저장해야 할 탐색 상태

코치는 일반 탐색에 대해 다음을 누적한다.

- 일자
- 플랫폼
- 프로그램 식별자 또는 안전한 별칭
- 자산 식별자 또는 안전한 별칭
- 기능/공격표면
- 테스트 관점
- Scope 확인 결과
- 테스트 결과 상태
- 핵심 관찰
- 새롭게 발견한 기능·흐름·신뢰경계
- 제외 영역
- 재확인 영역
- 다음 탐색 포인터
- 연결된 직무 브리핑 ITEM_ID
- 해당 단위에서 새롭게 습득한 실무 개념

프로그램별로 별도 집계한다.

```text
프로그램 P1
- 자산 수
- 확인한 기능 수
- 확인한 기능×관점 노드 수
- READY 수
- TESTED_EXPECTED 수
- TESTED_ANOMALY 수
- 후보 수
- 제출 수
- 유효 보고 수
- 마지막 다음 포인터
```

## 21. 공개 저장소 기록 경계

현재 블로그 저장소는 공개 저장소이므로 다음 정보는 공개 자산에 기록하지 않는다.

- 실제 자격증명·세션·토큰
- 테스트 계정의 개인정보
- 비공개 프로그램명과 Scope
- 내부 주소·비공개 자산
- 실제 요청·응답 원문 전체
- 공격 payload 원문
- 미공개 취약점의 구체적 재현 증거
- 타 사용자 데이터
- 고객 식별 정보

일반 탐색 기록은 공개 가능한 수준으로 자산·프로그램을 별칭화하고 관찰을 일반화한다.

취약점 후보가 생기면 상세 증거는 **플랫폼의 비공개 보고/초안 영역 또는 별도의 비공개 저장소**를 사용한다. 공개 블로그에는 후보 ID와 상태 같은 비민감 포인터만 남기고, 취약점이 적절히 공개될 수 있는 시점이 오기 전까지 기술 세부사항을 게시하지 않는다.

## 22. 다음날 시작 위치 결정

사용자가 **“오늘 버그바운티 알려줘.”** 라고 하면 코치는 다음 순서로 결정한다.

1. 진행 중인 `VERIFY / REPORT / NEEDS_INFO` 상태가 있는지 확인한다.
2. 있으면 신규 탐색보다 해당 후보 후속을 우선한다.
3. 없으면 PRIMARY 프로그램의 다음 포인터를 확인한다.
4. PRIMARY가 전환 조건을 만족하면 Reserve와 비교한다.
5. 직무 브리핑의 최신 `/take` 항목 중 미처리 보안 가설이 있는지 확인한다.
6. Scope·정책을 다시 확인한다.
7. 오늘 닫을 단일 `자산 × 기능 × 테스트 관점`을 지정한다.
8. 사용자에게 성공조건과 종료조건까지 포함한 단일 지시를 준다.

사용자에게는 원칙적으로 선택지를 여러 개 주지 않는다.

예시 형식:

```text
오늘 버그바운티 1단위
플랫폼/프로그램: P1
자산: A1
기능: 계정복구
관점: 소유권 경계
목표: 정상 기준과 권한 조건 1개를 비교
종료조건: 정상/이상/후보 중 하나로 분류하고 관찰 1줄 보고
```

## 23. 1단위 완료 후 추가시간 확장 규칙

한 단위를 완료한 뒤 추가 시간이 있으면 **완결된 다음 단위**를 새로 시작한다.

우선순위:

1. 활성 후보의 `VERIFY`
2. 제출 직전 후보의 `REPORT`
3. PRIMARY의 다음 `READY` 노드
4. 브리핑 `/take`에서 연결된 새 관점
5. Reserve 프로그램의 다음 노드

같은 기능을 관성적으로 계속 누르지 않는다. 매 단위마다 시작·종료 경계를 다시 만든다.

## 24. 성과 지표

장기 성과는 다음을 누적한다.

### 실행량

- 완료한 `EXPLORE` 단위 수
- 완료한 `VERIFY` 단위 수
- 완료한 `REPORT` 단위 수
- 연속 수행 일수

### 탐색 깊이

- 프로그램별 확인 자산 수
- 프로그램별 확인 기능 수
- 프로그램별 고유 `기능 × 관점` 노드 수
- 남은 `READY` 노드 수
- 재확인 트리거 발생 수

프로그램별 탐색 깊이는 다음 비율을 보조 지표로 사용한다.

```text
확인 완료 우선 노드 수 / 현재까지 식별된 우선 노드 수
```

공격표면을 새로 발견하면 분모가 늘어날 수 있으므로, 비율만 보지 않고 고유 노드 수도 함께 본다.

### 취약점 성과

- 이상 관찰 수
- 취약점 후보 수
- 실제 제출 수
- 유효 보고 수
- Duplicate 수
- Informative 수
- N/A/Invalid 수
- Resolved 수
- 보상 건수
- 누적 보상 금액

### 방법론 성과

- 기능군별 후보 발생률
- 테스트 관점별 후보 발생률
- 기능군 × 테스트 관점별 유효 보고율
- 반복적으로 N/A가 나는 접근
- 반복적으로 Duplicate가 나는 접근
- 실제 보상이 발생한 기능군·관점

### 직무 역량 성과

- 새로 이해한 서비스 구조
- 새롭게 익힌 취약점 발생 조건
- 새롭게 익힌 방어 메커니즘
- 보고서 작성 능력
- 개발·API·인증·세션·권한 구조에 대한 이해
- 테스트베드로 재현할 가치가 있는 패턴
- 자동화 코치로 넘길 반복 점검 아이디어

보상 금액은 결과 지표 중 하나일 뿐 단독 KPI로 사용하지 않는다.

## 25. 최소 운영 명령

실제 운영에서는 다음 두 문장만 기억한다.

### 시작

```text
오늘 버그바운티 알려줘.
```

코치는 기존 공격표면 지도, 후보 상태, 프로그램 전환 상태, 최신 직무 브리핑 `/take` 결과를 확인해 오늘의 단일 탐색을 지정한다.

### 종료 보고

```text
결과: 정상 | 이상 | 후보
관찰: 한 줄
```

코치는 그 보고를 바탕으로 상태를 갱신하고 다음 탐색 포인터를 결정한다.

## 26. 최초 1회 설정

실제 첫 운영 전에 다음만 한 번 등록한다.

1. HackerOne에서 현재 참여 가능한 보상 프로그램 후보
2. Find the Gap에서 현재 참여 가능한 보상 프로그램 후보
3. 각 후보의 최신 프로그램 페이지 또는 Scope·정책 정보
4. 필요한 테스트 계정 준비 여부
5. private program 여부

그 뒤 코치가 하드 게이트와 우선순위 기준으로 `PRIMARY / RESERVE`를 선정하고 첫 공격표면 지도를 만든다.

## 27. 운영 핵심 요약

- **취약점 발견이 완료조건이 아니다.** 정해진 탐색 사이클을 닫으면 완료다.
- **최소 단위는 기능 1개 × 테스트 관점 1개다.**
- **기본 1단위는 20~30분이다.**
- **Scope·정책 확인은 모든 실제 테스트보다 앞선다.**
- **정상 결과도 공격표면 지도에 의미 있는 완료 상태로 남긴다.**
- **후보가 생기면 일반 탐색과 분리해 VERIFY로 이동한다.**
- **검증된 후보만 REPORT로 이동한다.**
- **같은 노드는 재확인 트리거가 없으면 반복하지 않는다.**
- **프로그램을 최소 3개 노드 이상 탐색한 뒤 전환을 판단한다.**
- **최근 5단위가 저정보 상태이고 우선 노드가 소진되면 Reserve로 전환한다.**
- **직무 브리핑 `/take`는 공격 지시가 아니라 검증 대기 가설이다.**
- **실제 서비스 적용 전 Scope·정책·안전성을 다시 확인한다.**
- **공개 저장소에는 미공개 취약점 세부사항을 기록하지 않는다.**
- **사용자는 실행과 최소 결과 보고만 하고, 프로그램 선택·진행 상태·지도·다음 포인터는 코치가 관리한다.**
