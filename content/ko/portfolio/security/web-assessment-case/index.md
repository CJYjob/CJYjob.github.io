## 일반 점검 뒤에도 입력 처리 경로를 더 살폈다

웹 취약점 진단에서 기본 항목을 확인했지만 해당 페이지에서는 추가 취약점이 쉽게 드러나지 않았다. 요청·응답 확인에 이어 JavaScript가 값을 받아 화면과 실행 흐름에 사용하는 경로를 살폈다. 이 과정에서 값을 코드로 해석하는 `eval` 사용 지점을 확인했다.

조정한 값이 게시글에 저장되고, 그 게시글에 다시 접근하면 브라우저에서 스크립트가 실행됐다. 저장된 입력이 위험한 실행 지점에 도달하는 **저장형 XSS**였다. 페이지에서 실행됐다는 결과만 적지 않고, 저장 시점과 다시 읽는 시점, 실행 지점의 관계를 진단 산출물에 정리했다.

## 발견과 조치 확인은 같은 경로로 연결했다

| 단계 | 직접 수행한 일 |
| --- | --- |
| 분석 | 요청·응답과 JavaScript 입력 처리 경로 검토 |
| 재현 | 값을 저장한 뒤 게시글 재접속 시 스크립트 실행 확인 |
| 보고 | 재현 조건·영향·위험 함수 변경 필요성을 산출물에 기록 |
| 이행점검 | 조치 후 같은 경로에 다시 접근해 실행되지 않음을 확인하고 결과 작성 |

고객사에 대한 조치 요청 전달은 프로젝트의 담당 체계로 이뤄졌다. 직접 수행한 분석·산출물 작성·재검증을 기술하며, 요청 전달 전체를 혼자 수행한 것으로 표현하지 않는다.

## 원인에 맞춰 조치 방향을 적었다

브라우저에서 어떤 값이 표시되는 것과 그 값이 코드로 실행되는 것은 다르다. 이 사례에서는 입력이 실행 지점까지 전달되는 경로가 핵심이었다. 산출물에는 `eval` 등 실행 지점이 될 수 있는 함수의 변경 필요성을 기록했다. 개발 측 수정 후에는 같은 게시글 접근 경로에서 이전 동작이 재현되지 않는지 확인했다.

실제 요청값·서비스 기능·고객사 소스와 보고서는 공개하지 않는다. 다음은 수행 단계를 보여주기 위한 **합성 기록 예시**다. 실제 고객사 증적을 대신하는 자료는 아니다.

```text
관찰 A: 입력을 저장한 뒤 다시 조회하면 실행 지점에 전달된다.
판정 근거: 저장된 외부 입력이 코드로 해석되는 경로가 확인된다.
조치 방향: 입력을 코드로 실행하는 경로를 제거하고 데이터로 처리한다.
재검증: 이전과 동일한 저장·조회 경로에서 실행 여부를 확인한다.
기록: 조치 전·후 관찰과 재현 조건을 같은 항목에 연결한다.
```

## 현재 진단 업무로 이어진 부분

웹·앱·API 점검에서도 재현 조건, 영향, 조치 방향을 구분해 작성하고 완료된 항목은 다시 검증한다. Burp Suite로 요청·응답을 확인하며, 자동 도구의 탐지 결과와 직접 관찰한 사실을 구분한다. 과거 프로젝트 원본을 반출할 수 없는 만큼 공개 글에는 확인한 흐름을 설명하고, 원본 보고서를 공개 증빙으로 제시하지 않는다.
