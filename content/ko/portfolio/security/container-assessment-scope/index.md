## 이미지 목록보다 먼저 점검 책임을 정했다

컨테이너 점검을 준비하면서 표준 이미지, 외부 기반 이미지, 배포 과정에서 생성된 이미지를 같은 책임 범위로 볼 수 없다는 문제를 확인했다. 어떤 이미지를 누가 관리하는지와 이번 점검의 대상을 먼저 정해야 결과를 조치 담당자에게 연결할 수 있었다.

이 글은 [이미지 점검 Log](/log/security/infrastructure-assessment/container-image-scan-scope-01/)의 내용을 범위 정의에 사용할 수 있는 표로 정리한 결과물이다.

| 계층 | 확인할 질문 | 이미지 스캔만으로 답할 수 없는 것 |
| --- | --- | --- |
| 이미지 | 어떤 식별자의 구성요소를 검사했는가 | 실제 배포 여부, 실행 권한 |
| 실행 중 프로그램 | 어떤 설정과 계정으로 동작하는가 | 이미지 취약점 전체 |
| 호스트·플랫폼 | 조회 권한과 책임 범위는 어디까지인가 | 관리형 서비스의 내부 운영 상태 |
| 결과 보존 | 입력 식별자와 도구·DB 시점이 남는가 | 결과를 보관하지 않은 과거 실행의 상세 |

## 조회 권한과 설정 변경 권한을 분리했다

필요한 범위의 읽기 권한으로 이미지와 메타데이터를 확인했다. 스캔 기능을 활성화하거나 운영 설정을 바꾸는 작업은 별도의 책임과 권한이 필요했다. 연결 문제가 생겼을 때도 권한 문제와 실행 환경 문제를 구분해 확인했다.

선정한 이미지에 Trivy 점검을 실행한 경험이 있지만, 전체 환경 점검이나 모든 결과의 보존·조치를 완료한 것으로 확대하지 않는다. 임시 실행 환경에서는 세션이 끝나면 파일이 남지 않을 수 있어 실행과 보존을 별도로 확인해야 했다.

## 점검 계획에 남길 최소 정보

```text
입력: 가상 이미지 식별자와 고정 버전
선정 이유: 이번 범위에 포함된 관리 대상
조회 권한: 읽기 전용 / 승인된 실행 환경
출력: 도구 버전·DB 시점·실행 로그·결과 파일
분리 확인: 실행 설정 / 호스트 / 플랫폼 / 조치 담당자
완료 조건: 입력과 결과의 대응 및 보존 여부 확인
```

이 표와 서식은 특정 고객 환경의 구조를 설명하지 않는 독립적인 점검 계획 자료다. 이미지 점검을 여러 계층의 보안 평가 중 하나로 배치하는 데 목적이 있다.
