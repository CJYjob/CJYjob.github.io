## 서론

API 명세는 단순 URL 목록이 아니라 클라이언트 입력이 서버 내부 계층과 데이터 저장소를 거쳐 어떤 응답으로 변환되는지 추적하는 지도다.

## 요청 구성 요소

- HTTP Method: 요청의 의미를 나타낸다. GET은 리소스 표현 조회를 위한 safe method로 정의된다.
- Path: 서버 파일 경로라기보다 API가 노출하는 리소스의 URI 경로다.
- Query Parameter: 검색, 필터, 정렬, 페이징 등 요청 조건을 전달하는 데 흔히 사용한다.
- Body: 요청 또는 응답의 본문(payload)이다. Body라는 위치 자체가 암호화를 의미하지 않는다.
- Header: 인증 정보, 콘텐츠 형식 등 요청·응답의 부가 정보를 전달한다.

HTTPS를 사용하면 HTTP 내용이 TLS 전송 구간 보호를 받는다. 민감정보는 URL이 각종 로그와 기록에 남기 쉬운 특성까지 고려해 배치해야 한다.

## 응답 상태 코드

HTTP Status는 서버 자체의 상태가 아니라 요청 처리 결과를 클라이언트에 전달하는 표준 코드다.

- 1xx: 처리 과정의 정보
- 2xx: 성공
- 3xx: 리다이렉션
- 4xx: 요청 측 문제로 처리 불가
- 5xx: 서버 처리 실패

특히 401은 주로 인증 필요·실패, 403은 인증된 주체의 접근 불허를 나타내는 데 사용된다. 실제 서비스는 정보 노출 방지 등의 이유로 다른 상태 코드를 선택할 수 있으므로 코드만 보고 내부 구현을 확정하지 않는다.

## 서버 내부 흐름

일반적인 계층 구조에서는 다음과 같이 추적할 수 있다.

`클라이언트 → 공통 인증/검증 → Controller → Service → Repository → DB → Entity/조합 → DTO → 응답`

특정 리소스를 식별하는 Path Parameter와 조회 조건을 전달하는 Query Parameter의 역할을 구분한다. 조회 결과가 0건이라는 사실과 요청 자체가 잘못되었다는 사실도 구분해야 한다. 컬렉션 조회에서는 정상 처리 후 빈 배열을 반환하는 설계가 가능하다.

## 보안 연결

모바일 UI의 입력 제한은 보안 경계가 아니다. 정상 앱을 거치지 않고 API 요청을 구성할 수 있으므로 개수 제한, 형식, 허용 범위 등 중요한 조건은 서버에서도 검증해야 한다.

또한 요청 서명 인증이 성공했다는 사실과 특정 객체에 대한 접근 권한은 별개의 문제다. API를 읽을 때 `누가 요청했는가`와 `그 주체가 이 객체를 사용할 수 있는가`를 분리한다.

## 결론

API 명세는 `Method → Path → 입력 → 공통 검증 → 비즈니스 로직 → 데이터 접근 → 응답 → 오류` 순서로 읽으면 내부 흐름과 보안 경계를 함께 그릴 수 있다.
