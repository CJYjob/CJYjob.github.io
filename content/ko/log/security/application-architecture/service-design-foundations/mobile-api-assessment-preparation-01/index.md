## 서론

설계 자료만 확보된 상태에서는 바로 공격 요청을 만들기보다 실제 점검 대상과 접근 조건부터 확정해야 한다. 운영 중인 앱인지, 개발·검증 환경인지, 설치 파일이 존재하는지, API 단독 점검이 허용되는지에 따라 점검 방법이 크게 달라진다.

## 1. 가장 먼저 확정할 것: 점검 대상과 환경

담당자에게 우선 확인할 내용은 다음과 같다.

- 이번 점검 대상이 모바일 앱 전체인지, 신규 API 기능인지, 둘 다인지
- 점검할 환경이 개발·테스트·QA·운영 중 어디인지
- 해당 환경에 접근하려면 사내망, VPN, 허용 IP 등 별도 접속 조건이 필요한지
- 운영 환경에 대한 변조·대량 요청 등이 금지되어 있는지
- Android/iOS 중 실제 제공 가능한 플랫폼과 빌드가 무엇인지

문서에 여러 환경이 존재한다고 적혀 있어도 실제 점검용 환경을 임의로 선택하지 않는다. 점검 허용 범위를 담당자에게 명시적으로 확인한 뒤 그 범위 안에서만 수행한다.

## 2. 앱 자산과 API 단독 점검의 구분

모바일 취약점 점검이라면 앱 설치 파일이나 테스트 설치 경로가 필요하다. 앱이 아직 제공되지 않는 경우 API가 먼저 열려 있다면 API 점검부터 시작할 수 있지만, 이 경우에는 클라이언트 저장소·권한·Deep Link·난독화·인증서 고정 같은 앱 자체 항목은 점검할 수 없다.

따라서 앱이 없는 상태에서는 담당자에게 다음 두 가지를 분리해 묻는다.

1. 현재 모바일 앱 빌드를 제공할 수 있는가.
2. 앱 제공 전이라면 이번 단계에서 API 단독 보안 점검을 먼저 수행해도 되는가.

## 3. clientId와 API 비밀값을 추측하지 않는다

요청 서명 기반 인증에서 `clientId`는 어떤 비밀값을 사용할지 식별하는 공개 식별자 역할을 할 수 있고, `apiKey` 같은 값은 실제 서명 계산에 필요한 공유 비밀값 역할을 할 수 있다. 그러나 이름만으로 발급 단위를 단정하면 안 된다.

특히 다음은 별도 확인이 필요하다.

- clientId가 사용자, 단말, 앱 설치, 앱 버전, 애플리케이션 전체 중 무엇을 식별하는가
- 비밀값이 각 클라이언트마다 다른가, 여러 설치본이 공유하는가
- 앱은 최초 설치·등록 과정에서 값을 발급받는가, 빌드에 포함하는가
- 분실·폐기·교체 절차가 있는가

API 요청을 변조하려면 정상 요청을 만드는 데 필요한 자격정보가 있어야 한다. 서명 대상 필드를 수정하면 기존 서명이 무효화되는 구조라면, 단순 프록시 변조만으로는 정상적인 변조 요청을 만들 수 없고 테스트용 키나 서명 로직을 확보해야 할 수 있다.

## 4. 프록시 점검은 먼저 시도하고, 막히는 원인을 분리한다

Burp Suite나 Charles 같은 프록시로 HTTPS 트래픽을 가로채기 위해 테스트 단말에 프록시 CA 인증서를 설치하는 것은 기본 준비다. 그러나 단말에 인증서가 있다는 사실만으로 모든 앱의 통신을 복호화할 수 있는 것은 아니다.

차단 원인은 대표적으로 다음과 같이 나뉜다.

- 앱이 사용자 추가 CA를 신뢰하지 않음
- Certificate Pinning으로 특정 서버 인증서나 공개키를 고정함
- 앱 내부 네트워크 설정이 프록시 경로를 허용하지 않음
- 요청 자체에 별도 서명이 있어 내용 변경 후 인증이 실패함

따라서 정상 앱이 확보되면 먼저 직접 프록시 캡처를 시도한다. 캡처가 실패할 때만 원인을 확인하고, 허가된 범위에서 점검용 빌드·우회 방법·테스트 인증서·서명 테스트 지원 등을 요청한다.

## 5. API 문서는 실제 접근 가능 여부를 먼저 확인한다

설계서가 있어도 현재 실행 중인 API와 완전히 일치한다고 보장할 수 없다. 접근 가능한 점검 환경이 정해지면 API 문서 페이지나 OpenAPI 명세가 실제로 열리는지 확인하고, 문서상 엔드포인트와 실행 환경을 대조한다.

관리·문서 페이지가 IP 제한 대상으로 설계되어 있다면 제한이 정상 작동하는지도 확인한다. 여기서 IP CIDR 제한은 특정 IP 주소 대역만 접근하도록 허용하는 네트워크 수준의 접근 제한이다.

## 6. 인증 제외 경로는 "취약"이 아니라 공개 범위 검증 대상이다

일반적인 서버 설계에서는 health, API 문서, 오류 처리, CORS preflight 같은 공통 경로를 주 인증 체계에서 제외할 수 있다. 인증 제외 자체가 곧 취약점은 아니다.

점검에서는 다음을 확인한다.

- health가 단순 생존 상태를 넘어 내부 시스템 정보까지 노출하는가
- error 처리에서 stack trace, DB 정보, 내부 경로 등이 노출되는가
- API 문서가 의도한 네트워크 범위 밖에서 열리는가
- CORS preflight 처리와 실제 CORS 정책이 의도와 일치하는가

`인증 없음`과 `누구에게나 모든 정보를 공개해도 됨`은 같은 뜻이 아니다.

## 7. 테스트 콘텐츠보다 권한 차이 자료가 더 먼저 필요할 수 있다

조회형 서비스라면 접근 가능한 환경에서 정상 목록을 직접 확인해 테스트 데이터를 확보할 수 있다. 따라서 일반 공개 데이터만 다루는 기능에서는 담당자에게 개별 콘텐츠 ID를 미리 요구할 필요가 없을 수 있다.

반면 인가 취약점을 판단하려면 "누가 무엇에 접근할 수 없어야 하는가"라는 기준이 반드시 필요하다. 따라서 다음은 담당자에게 확인해야 한다.

- 사용자나 클라이언트에 권한 등급 차이가 있는가
- 특정 사용자·클라이언트만 접근 가능한 데이터가 있는가
- 비활성·미공개·관리용 리소스가 존재하는가
- 권한이 다른 테스트 주체를 두 개 이상 제공할 수 있는가

권한 차이가 없는 공개 조회 서비스라면 단순 ID 변경으로 다른 공개 리소스가 조회되는 것을 IDOR/BOLA로 판정하면 안 된다.

## 8. 로그와 내부 관측 데이터는 기본 요청사항이 아니다

외부 또는 모바일 관점의 점검이라면 서버 로그, DB, 내부 trace를 처음부터 요구하지 않고 외부에서 관찰 가능한 동작으로 먼저 검증한다. 내부 로그는 다음과 같은 경우에 보조 자료로 요청할 수 있다.

- 외부 응답만으로 서버 처리 여부를 구분할 수 없음
- 재현은 되지만 원인 분석에 내부 확인이 필요함
- 담당자와 공동 검증하는 단계로 넘어감

인프라·CI/CD·IAM 같은 영역도 모바일 점검 범위 밖이라면 별도 인프라 점검으로 분리한다.

## 9. 점검 시작 전 최소 요청사항

실제 착수 전에 담당자에게 확인할 최소 항목은 다음과 같다.

1. 점검 대상: 모바일 앱 전체 / API 기능 / 둘 다
2. 점검 환경과 접근 방법: 테스트·QA·운영 여부, VPN·사내망·허용 IP 필요 여부
3. 앱 자산: Android/iOS 테스트 빌드 또는 설치 경로
4. API 단독 점검 허용 여부: 앱이 아직 준비되지 않았을 경우
5. 인증정보 발급 방식: client 식별자와 요청 서명용 비밀정보의 발급 단위와 테스트 자격정보 제공 가능 여부
6. 권한 모델: 사용자·클라이언트별 권한 차이와 권한이 다른 테스트 주체 제공 가능 여부
7. 점검 제한: 대량 요청, 운영 데이터 변경, 콘텐츠 다운로드 등 금지·제한 행위

프록시 우회 지원, 테스트 콘텐츠 목록, 내부 로그 등은 실제 점검을 시작한 뒤 필요성이 확인되었을 때 추가 요청해도 된다.

## 10. 착수 후 첫 작업

환경과 자격정보가 확보되면 첫 작업은 공격이 아니라 정상 요청 기준선 확보다.

`정상 앱 또는 API 호출 → 요청/응답 캡처 → 인증 요소 확인 → 리소스와 권한 관계 확인 → 변조 후보 정의 → 한 요소씩 변경 → 응답 비교`

이 기준선이 있어야 이후 인증, Replay, 인가, 입력값 검증, 외부 콘텐츠 접근, 모바일 클라이언트 저장·노출 점검 결과를 정상 동작과 비교할 수 있다.

## 결론

점검 준비 단계에서 가장 중요한 것은 공격 기법 목록이 아니라 `무엇을, 어느 환경에서, 어떤 권한으로 점검할 수 있는가`를 확정하는 것이다. 확보되지 않은 환경·자격정보·권한 모델을 추측하지 않고, 외부에서 직접 확인할 수 있는 것은 먼저 확인한 뒤 필요한 정보만 담당자에게 요청한다.
