## HMAC의 역할

HMAC은 Hash-based Message Authentication Code의 약자다. 송신자와 서버가 공유하는 비밀키를 이용해 메시지에 대한 인증 코드를 계산한다.

```text
요청 데이터 + 공유 비밀키
        ↓ HMAC
      서명값
```

서버는 자신이 가진 같은 키와 동일한 서명 대상 데이터를 이용해 HMAC을 다시 계산하고, 전달받은 서명과 비교한다. 일치하면 **서명 대상 데이터가 중간에 달라지지 않았으며 해당 비밀키를 사용할 수 있는 주체가 서명을 생성한 것으로 볼 근거**가 생긴다.

HMAC 자체는 암호화가 아니므로 요청 내용을 숨기는 기능은 없다. 전송 내용의 기밀성은 TLS 같은 별도 보호 계층이 담당한다.

## Timestamp와 Nonce

정상적으로 서명된 요청도 공격자가 그대로 복사해 다시 전송할 수 있다. 이를 Replay 공격이라고 한다.

Timestamp는 요청이 허용된 시간 범위 안에서 생성되었는지 확인하는 데 사용할 수 있다. 오래전에 수집한 요청을 장기간 뒤에 재사용하는 공격 범위를 줄이지만, 허용 시간창 안에서 같은 요청을 다시 보내는 것까지 Timestamp 하나만으로 막지는 못한다.

Nonce는 요청마다 사용하는 일회성 값이다. 서버가 이미 처리한 nonce를 기억하고 같은 값의 재사용을 거부하면 시간창 안에서의 동일 요청 재전송을 막는 데 사용할 수 있다.

```text
서명 검증
+ Timestamp 유효성
+ Nonce 미사용 여부
= 요청의 진위·무결성 + 재사용 제한을 결합한 검증
```

## 여러 애플리케이션 인스턴스와 Nonce 저장소

Nonce를 한 애플리케이션 프로세스의 로컬 메모리에만 저장하면 그 프로세스는 자신이 본 nonce만 기억한다. 여러 인스턴스가 요청을 나눠 처리하는 환경에서는 인스턴스 간 상태가 공유되지 않는다면 다른 인스턴스가 동일 nonce를 처음 보는 값으로 판단할 가능성이 있다.

따라서 `인메모리 nonce 저장 = replay가 반드시 가능하다`는 결론은 성립하지 않는다. 단일 인스턴스인지, 요청이 특정 인스턴스에 고정되는지, 외부 공유 저장소가 있는지 등 실제 배치와 라우팅을 확인해야 한다.

여러 인스턴스가 동일한 원자적 저장소를 공유하면 nonce 사용 여부를 공통으로 판단하도록 설계할 수 있다. Redis 같은 메모리 중심 데이터 저장소가 이 용도로 사용될 수도 있지만, Redis 사용 여부만으로 replay 방어의 안전성을 판정할 수는 없다. TTL, 원자적 등록, 장애 시 정책과 같은 구현 조건도 확인해야 한다.

## 비밀키와 비밀번호 저장의 차이

로그인 비밀번호는 서버가 원문을 다시 알아낼 필요가 없다. 일반적으로 salt와 비밀번호용 KDF를 사용해 검증 가능한 값을 저장하고, 사용자가 입력한 비밀번호를 같은 검증 과정에 넣어 비교한다.

HMAC 비밀키는 서버가 새로운 HMAC 값을 계산할 수 있는 **사용 가능한 key material**을 필요로 한다. 원래 비밀키 대신 양쪽이 `Hash(secret)`을 HMAC 키로 사용하도록 프로토콜을 설계하는 것도 기술적으로 가능하지만, 그 경우 `Hash(secret)` 자체가 HMAC을 생성할 수 있는 새로운 비밀키가 된다. 공격자가 그 값을 얻으면 원래 secret을 복원하지 않고도 유효한 HMAC을 만들 수 있으므로 단순한 비밀번호 검증값과 성질이 다르다.

따라서 HMAC 키 또는 그와 동등한 key material은 암호화 저장, 접근 통제, 키 관리 시스템, 교체 정책 등 **복구·사용 가능한 비밀정보에 맞는 보호**가 필요하다.

KDF는 Key Derivation Function의 약자다. 비밀번호 저장에서는 빠른 일반 해시만 사용하는 대신 salt와 계산 비용을 적용하는 비밀번호용 KDF를 사용해 무차별 대입 비용을 높이는 방식이 일반적이다.

## KMS, HSM, Secret Manager

- KMS(Key Management Service/System): 암호키의 생성, 저장, 사용 권한, 교체 등 키 생명주기를 관리한다.
- HSM(Hardware Security Module): 암호키를 강하게 보호하고 암호 연산을 수행하도록 설계된 보안 하드웨어다. KMS와 함께 사용될 수 있지만 둘은 같은 개념이 아니다.
- Secret Manager: API 키, DB 자격증명, 토큰 등 애플리케이션 비밀정보를 중앙에서 저장·접근 관리하는 시스템이다.
- Rotation: 비밀키나 자격증명을 정책에 따라 새 값으로 교체하고 기존 값의 사용을 종료하는 운영 과정이다.

## 인증·무결성·Replay 방어·인가 구분

HMAC이 `사용자 로그인`과 항상 같은 주체를 인증한다고 가정하면 안 된다. HMAC 키가 애플리케이션 클라이언트, 외부 시스템, 장치 등 다른 주체에 귀속될 수도 있다.

```text
클라이언트 인증: 이 자격증명을 가진 주체인가?
요청 무결성: 서명 대상 데이터가 변조되지 않았는가?
Replay 방어: 과거의 정상 요청을 다시 쓰는 것은 아닌가?
사용자 인증: 현재 최종 사용자는 누구인가?
인가: 그 주체가 이 작업을 수행할 권한이 있는가?
```

한 메커니즘이 여러 역할을 일부 겸할 수 있지만 보안 진단에서는 각각의 보장 범위를 분리해서 확인한다.

## 일반적인 인증 제외 경로를 읽는 법

일부 API 서버는 상태 확인, API 문서, 오류 처리, 브라우저의 CORS preflight 같은 특정 요청을 공통 인증 필터에서 제외할 수 있다. `인증 제외 = 모든 정보를 공개해도 안전하다`는 뜻은 아니다.

- Health: 서비스 상태 확인용 경로. 민감한 내부 상태가 과도하게 노출되는지 확인한다.
- API 문서 UI/명세: 개발 편의를 위한 기능. 운영 환경 노출 범위와 접근 제어를 별도로 확인한다.
- Error 처리 경로: 오류 응답을 처리하기 위해 인증 흐름과 다르게 동작할 수 있다. 스택 트레이스·내부 정보 노출 여부를 확인한다.
- CORS preflight: 브라우저가 실제 cross-origin 요청 전에 허용 method/header/origin 등을 확인하기 위해 보내는 OPTIONS 요청이다. CORS는 브라우저의 교차 출처 요청 제어 정책이지 서버 인증을 대체하는 보안 경계가 아니다.

## 공격자 관점

- 서명 대상에서 중요한 요청 요소가 빠져 있는가
- Timestamp 허용창이 과도하게 넓은가
- Nonce가 여러 처리 인스턴스 사이에서 일관되게 검증되는가
- 비밀키 또는 동등한 key material이 앱, 로그, 저장소에서 추출 가능한가
- 인증 제외 경로가 내부 정보나 관리 기능을 노출하는가

## 방어자 관점

- 서명 대상과 정규화 규칙을 명확히 정의한다.
- Timestamp와 nonce를 함께 사용할 경우 저장 기간과 허용 시간창을 일관되게 설계한다.
- 분산 환경에서는 nonce 등록의 원자성과 공유 범위를 검증한다.
- 비밀키의 저장·접근·교체·감사를 관리한다.
- HMAC 검증과 사용자 인증·인가를 각각 필요한 경계에 적용한다.
