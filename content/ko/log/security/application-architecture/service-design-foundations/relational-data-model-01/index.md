## 서론

서비스 설계의 데이터 모델을 읽을 때 테이블 이름만 보는 것이 아니라, 어떤 사실을 독립적으로 저장하고 어떤 관계를 별도 테이블로 표현하는지 확인한다.

## 테이블과 컬럼 코멘트

테이블·컬럼 comment는 동작 로직이 아니라 스키마에 붙는 설명 메타데이터다. 이름만으로 의미가 불분명한 값의 단위, 용도, 관계를 설명해 DB를 직접 보는 사람도 의도를 파악할 수 있게 한다.

## 정규화와 관계

정규화의 목적을 저장공간 절약만으로 이해하면 좁다. 핵심은 같은 사실을 여러 곳에 중복 저장하면서 발생하는 수정 누락과 불일치를 줄이는 데 있다.

- `1:N`: 한 개체 하나가 다른 개체 여러 개와 관계를 맺는다.
- `N:M`: 양쪽 개체 모두 여러 상대와 관계를 맺을 수 있다.
- 중간 테이블: N:M 관계를 관계형 DB에서 표현하기 위한 대표적인 구조다.
- 외래키(FK): 한 테이블의 값이 다른 테이블의 유효한 행을 참조하도록 참조 무결성을 보장하는 수단이다.

외래키가 보장하는 것은 "존재하는 대상을 참조하는가"이지 "현재 요청자가 그 대상을 사용할 권한이 있는가"가 아니다. 후자는 애플리케이션의 인가 문제다.

## Entity와 DTO 연결

Entity는 단순히 DB 한 행을 복사한 그릇이라는 의미보다, 영속성 계층에서 애플리케이션 객체와 DB 상태를 연결하고 관리하는 객체라는 관점이 중요하다. DTO는 전달 목적의 객체이며 하나의 Entity를 축약할 수도 있고 여러 Entity와 관계 데이터를 조합할 수도 있다.

따라서 내부 저장 모델의 컬럼명과 외부 API 응답의 필드명이 같을 필요는 없다. 내부 경로나 상태값을 서버에서 가공한 뒤 외부용 DTO에 다른 형태로 담는 것도 자연스럽다.

## 보안 연결

숫자형 식별자나 관계키가 API에 노출될 때 값을 변경해 다른 객체를 조회할 수 있다는 사실만으로 취약점은 아니다. 원래 접근할 권한이 없는 객체가 식별자 변경만으로 반환되는지를 확인해야 IDOR/BOLA 같은 인가 문제로 판단할 수 있다.

## 결론

데이터 모델은 `개체 → 관계 → 참조 무결성 → 애플리케이션 객체 → 외부 전달 객체` 순으로 읽는다. 정규화와 FK는 데이터 일관성을 위한 장치이며 사용자 권한을 대신하지 않는다.
