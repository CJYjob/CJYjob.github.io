## Redis는 무엇인가

Redis는 운영체제 위에서 실행되는 독립적인 데이터 서버 프로세스다. 애플리케이션과 같은 호스트에서 실행할 수도 있고, 별도 호스트나 관리형 서비스로 분리할 수도 있다.

```text
같은 호스트: App process + Redis process
분리 구성:   App host → network → Redis host
```

DBMS와 마찬가지로 클라이언트 요청을 받아 데이터를 읽고 쓰는 독립 서버 프로그램이라는 관점이 도움이 된다. Redis는 메모리 중심 데이터 구조와 빠른 접근 특성 때문에 캐시 계층으로 자주 사용된다.

## DBMS와 OS도 캐시하는데 Redis는 무엇이 다른가

DBMS와 OS도 메모리를 적극적으로 활용한다. DBMS는 자주 쓰는 데이터 페이지와 인덱스 등을 자체 버퍼에 보관할 수 있고, OS도 파일과 디스크 블록을 페이지 캐시에 유지할 수 있다.

따라서 Redis를 단순히 `DB가 쓰는 메모리 영역을 더 넓히는 도구`라고 이해하면 부정확하다.

핵심 차이는 **캐시의 의미와 제어 주체**에 있다.

- OS 캐시: 어떤 파일·페이지가 자주 쓰이는지를 운영체제가 관리한다.
- DBMS 캐시: DB 내부 데이터 페이지·인덱스·실행 계획 등을 DBMS가 관리한다.
- Redis 캐시: 애플리케이션이 `어떤 데이터를 어떤 키로 어떤 형태로 얼마 동안 보관할지`를 직접 설계한다.

예를 들어 DBMS는 필요한 데이터가 메모리에 있어도 SQL 해석, 인덱스 탐색, 조인·정렬·집계 같은 DB 처리 과정을 수행할 수 있다. Redis에는 그 결과를 미리 계산한 형태로 저장해 둘 수 있으므로 동일한 DB 연산 자체를 생략할 수 있다.

```text
DB 조회
App → DB → SQL/조회/조인/정렬/집계 → 결과

캐시 hit
App → Redis → 준비된 값 → 결과
```

즉 Redis의 가치는 `메모리를 더 많이 쓴다`보다 **애플리케이션이 재사용할 결과를 별도 데이터 계층에 준비해 두고 비싼 처리 경로를 건너뛸 수 있다**는 데 있다.

## 별도 서버인데 왜 빠를 수 있는가

별도 Redis 서버를 사용하면 네트워크 왕복 시간이 추가된다. 따라서 네트워크 비용이 사라지는 것은 아니다.

그럼에도 캐시가 유리할 수 있는 이유는 비교 대상이 단순한 `RAM 대 SSD`가 아니기 때문이다. 작은 DB 단건 조회는 Redis를 붙여도 이득이 거의 없을 수 있다. 반대로 반복되는 조인·집계·정렬처럼 비싼 조회라면 네트워크 왕복을 포함해도 준비된 Redis 값을 읽는 편이 훨씬 빠를 수 있다.

따라서 캐시 도입 여부는 실제 응답시간, 쿼리 비용, 요청 빈도와 부하를 측정해 판단해야 한다.

## Cache-Aside 흐름

1. 애플리케이션이 Redis에서 키를 조회한다.
2. 값이 있으면 Cache Hit로 바로 사용한다.
3. 없으면 Cache Miss다.
4. 원본 DB를 조회한다.
5. 결과를 Redis에 저장한다.
6. 이후 동일한 데이터가 필요하면 캐시를 재사용한다.

## 갱신과 정합성

DB의 원본이 변경된 뒤 Redis에 오래된 값이 남을 수 있다. 이를 관리하기 위해 TTL 만료, 원본 변경 시 캐시 삭제, 캐시 동시 갱신 등의 정책을 사용한다.

캐시 도입은 성능과 함께 키 설계, 메모리 관리, 장애 fallback, 캐시 스탬피드, 데이터 정합성 같은 새로운 복잡성을 만든다.

## 공격자 관점

- Redis의 불필요한 외부 노출
- 인증·네트워크 접근 제어 오류
- 사용자나 테넌트 경계가 빠진 캐시 키
- 오래된 권한 정보의 캐시

## 방어자 관점

- 네트워크 접근 최소화
- 인증과 전송 보호
- 민감 데이터 캐시 최소화
- 키에 필요한 권한 문맥 반영
- TTL·무효화·장애 상황 검증
