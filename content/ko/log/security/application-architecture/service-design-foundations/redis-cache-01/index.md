## Redis는 무엇인가

Redis는 운영체제 위에서 실행되는 독립적인 데이터 서버 프로세스다. 애플리케이션과 같은 호스트에서 실행할 수도 있고 별도 호스트나 관리형 서비스로 분리할 수도 있다.

```text
같은 호스트: App process + Redis process
분리 구성:   App host → network → Redis host
```

DBMS와 마찬가지로 클라이언트 요청을 받아 데이터를 읽고 쓰는 독립 서버 프로그램이라는 관점이 도움이 된다. 다만 Redis는 메모리 중심 데이터 구조와 빠른 접근 특성 때문에 캐시 용도로 널리 사용된다.

## 별도 서버인데 왜 빠를 수 있는가

별도 Redis 서버를 사용하면 네트워크 왕복 시간이 추가된다. 따라서 `네트워크를 타니까 비용이 없다`는 뜻은 아니다.

그럼에도 캐시가 유리한 경우가 많은 이유는 비교 대상이 단순한 `RAM 대 SSD 읽기 속도`가 아니기 때문이다. DB 요청에는 네트워크 통신뿐 아니라 SQL 파싱·계획, 인덱스 탐색, 여러 행 처리, 조인·정렬·집계, 잠금·동시성 제어, 결과 생성 같은 작업이 포함될 수 있다. DB도 자체 메모리 버퍼와 OS 페이지 캐시를 사용하므로 실제 조회가 항상 물리 디스크까지 내려가는 것도 아니다.

Redis 캐시는 미리 계산하거나 조회한 값을 단순한 key-value 형태로 보관해 이런 DB 처리 자체를 건너뛰는 데 가치가 있다.

```text
DB 조회:    App → network → DB → query 처리/데이터 접근 → 결과
캐시 hit:   App → network → Redis → 메모리의 준비된 값 → 결과
```

따라서 성능은 실제 지연시간과 부하를 측정해서 판단해야 한다. 작은 DB 조회에서는 캐시 이점이 거의 없을 수도 있고, 비싼 조회가 반복되는 상황에서는 네트워크 비용을 포함해도 Redis가 훨씬 유리할 수 있다.

## Cache-Aside 흐름

1. 애플리케이션이 Redis에서 키를 조회한다.
2. 값이 있으면 Cache Hit로 바로 사용한다.
3. 없으면 Cache Miss다.
4. 원본 DB를 조회한다.
5. 결과를 Redis에 저장한다.
6. 이후 동일한 데이터가 필요하면 캐시를 재사용한다.

## 갱신과 정합성

DB의 원본이 변경된 뒤 Redis에 오래된 값이 남을 수 있다. 이를 관리하기 위해 TTL 만료, 원본 변경 시 캐시 삭제, 캐시 동시 갱신 등의 정책을 사용한다.

캐시 도입은 성능과 함께 새로운 복잡성도 만든다. 키 설계, 메모리 관리, 장애 fallback, 캐시 스탬피드, 데이터 정합성 등을 함께 고려해야 한다.

## 공격자 관점

- Redis의 불필요한 외부 노출
- 인증·네트워크 접근 제어 오류
- 사용자나 테넌트 경계가 빠진 캐시 키
- 오래된 권한 정보의 캐시

## 방어자 관점

- 네트워크 접근 최소화
- 인증과 전송 보호
- 민감 데이터 캐시 최소화
- 키에 필요한 권한 문맥 반영
- TTL·무효화·장애 상황 검증
