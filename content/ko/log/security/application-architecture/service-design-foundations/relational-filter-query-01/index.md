## 서론

SQL을 문법만 따라가면 왜 그런 쿼리가 필요한지 놓치기 쉽다. 먼저 사용자가 원하는 기능을 논리 조건으로 바꾸고, 그 조건을 현재 데이터 구조에서 어떻게 검증할지 생각한다.

## 기능에서 논리식으로

여러 분류 그룹에서 복수 항목을 선택하는 일반적인 필터를 가정한다. 같은 그룹 안의 복수 선택을 선택지 확장으로 해석하면 OR가 되고, 서로 다른 그룹의 조건을 모두 요구하면 AND가 된다.

예를 들어 요구사항이 다음과 같을 수 있다.

`(그룹 A의 항목 1 OR 항목 2) AND (그룹 B의 항목 3)`

중요한 점은 이것이 먼저 기능 규칙이고 SQL은 그 규칙의 구현 수단이라는 것이다.

## 왜 단순 WHERE AND/OR로 끝나지 않는가

관계형 중간 테이블에서는 한 리소스의 여러 속성이 서로 다른 행에 저장될 수 있다. 한 행이 동시에 서로 다른 여러 태그 값을 가질 수 없으므로, 단일 행에 모든 AND 조건을 직접 적용하는 방식으로는 의도를 표현하기 어렵다.

그래서 문제를 다음 순서로 바꾼다.

1. 사용자가 선택한 값과 일치하는 관계 행만 후보로 남긴다.
2. 남은 행을 리소스 식별자별로 묶는다.
3. 같은 분류 그룹에서 여러 값이 일치해도 그룹 하나를 만족한 것으로 센다.
4. 각 리소스가 사용자가 요구한 모든 분류 그룹을 만족했는지 검사한다.
5. 통과한 리소스 식별자를 결과로 선택한다.

## SQL의 논리적 처리 순서

이 유형의 쿼리를 이해할 때는 작성 순서보다 다음 논리 흐름이 유용하다.

`FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT`

- `FROM/JOIN`: 관계 테이블과 분류 정보를 연결한다.
- `WHERE`: 사용자가 선택하지 않은 값을 먼저 제거한다.
- `GROUP BY`: 리소스별로 남은 관계를 묶는다.
- `HAVING`: 묶인 그룹이 요구한 분류 조건을 모두 만족하는지 검사한다.
- `SELECT`: 최종적으로 필요한 식별자나 컬럼을 반환한다.

`WHERE`는 그룹화 전 개별 행을 거르고, `HAVING`은 그룹화 후 그룹을 거른다는 차이가 핵심이다.

## COUNT(DISTINCT ...)가 필요한 이유

같은 분류 그룹에서 두 값이 동시에 일치하더라도 기능적으로는 그 그룹 조건 하나를 충족한 것이다. 따라서 중복된 그룹을 제거한 뒤 개수를 세어야 한다.

또한 숫자 비교 전에 WHERE가 사용자가 선택한 값만 남기므로, 선택하지 않은 다른 그룹이 우연히 같은 개수를 만들어 통과하는 문제를 피할 수 있다.

## 보안 연결

필터 개수 제한이나 허용 값 검증은 클라이언트 UI뿐 아니라 서버에서 확인해야 한다. 존재하지 않는 식별자, 중복 값, 과도하게 긴 입력 등 비정상 입력에서 로직이 깨지거나 내부 오류 정보가 노출되는지도 검증 포인트다. 파라미터 바인딩을 사용하는 설계와 실제 구현이 일치하는지는 별도로 확인한다.

## 결론

기능을 SQL로 옮길 때는 `기능 요구사항 → 논리식 → 데이터가 행에 저장되는 방식 → 후보 제한 → 그룹화 → 그룹 조건 → 결과` 순서로 사고한다. 이 과정은 비즈니스 로직 취약점을 분석할 때도 개발 의도와 실제 데이터 처리의 차이를 찾는 기반이 된다.
