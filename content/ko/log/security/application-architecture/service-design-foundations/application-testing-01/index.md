## 서론

설계 문서의 테스트 전략을 읽으면 개발자가 어떤 로직을 변경에 민감한 경계로 보고 있는지 파악할 수 있다. 기능 테스트와 보안 테스트는 겹치는 부분이 있지만 목적이 동일하지는 않다.

## 단위 테스트

단위 테스트는 작은 로직을 분리해 정해진 입력에 기대한 출력이 나오는지 검증한다. 예를 들어 다음과 같은 대상이 될 수 있다.

- 복수 조건 필터가 정의된 AND/OR 규칙을 유지하는가
- 서명 생성기가 고정 입력에서 기대한 검증값을 만드는가
- 텍스트 기반 재생목록의 리소스 주소 가공이 정확한가
- 시간 조건에 따른 활성 상태 판정이 경계값에서도 맞는가
- 요청 인증에서 정상·비정상 검증 결과가 의도대로 나오는가

고정 입력과 기대 출력을 잠가 두면 구현을 수정했을 때 기존 계약이 깨졌는지 빠르게 알 수 있다.

## 통합 테스트

통합 테스트는 함수 하나보다 실제 애플리케이션 구성에 가까운 상태에서 여러 계층이 연결되어 동작하는지 확인한다. Spring 기반 애플리케이션에서는 애플리케이션 컨텍스트와 MVC 요청 처리 계층을 함께 올려 HTTP 요청과 응답을 검증하는 방식을 사용할 수 있다.

이를 통해 `요청 → Controller → Service → 의존 컴포넌트 → 응답`의 연결이 실제 설정에서도 동작하는지 확인한다.

## Fake와 DI

테스트가 실제 외부 시스템에 매번 의존하면 네트워크 상태, 외부 장애, 비용 같은 변수가 테스트에 섞인다. 그래서 외부 클라이언트를 인터페이스 뒤에 두고 테스트에서는 같은 계약을 만족하는 Fake 구현을 주입할 수 있다.

`운영: Service ← 실제 외부 Client`

`테스트: Service ← Fake Client`

Service가 구체 구현을 직접 생성하지 않고 필요한 의존성을 외부에서 받는 DI 구조이기 때문에 이런 교체가 쉬워진다. 인터페이스·구현체·DI가 테스트 가능성과 직접 연결되는 사례다.

## 개발 테스트와 보안 테스트

개발 테스트는 주로 "설계한 기능이 정상적으로 유지되는가"를 묻는다. 보안 테스트는 "공격자가 비정상 입력, 순서, 상태 전환을 만들었을 때도 경계가 유지되는가"를 추가로 묻는다.

예를 들어 정상 서명 성공과 잘못된 서명 실패를 단위 테스트했다고 해서 Replay, 상태 공유 문제, 인가 누락, 경계값 조작까지 검증되었다고 볼 수 없다.

## 결론

테스트 전략은 단순 품질 관리 항목이 아니라 시스템의 중요 로직과 의존 경계를 보여준다. 보안 진단에서는 기존 기능 테스트가 무엇을 보장하는지 확인한 뒤, 그 테스트가 가정하지 않은 공격자 입력과 상태를 추가로 탐색한다.
