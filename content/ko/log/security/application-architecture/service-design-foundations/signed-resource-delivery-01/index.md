## 서론

대용량 콘텐츠 서비스에서는 API 서버가 메타데이터와 접근 제어를 담당하고 실제 콘텐츠 전송은 CDN이 담당하도록 역할을 분리할 수 있다. 이렇게 하면 큰 전송 트래픽이 애플리케이션 서버와 DB 처리 부하에 직접 섞이지 않는다.

## 재생목록과 세그먼트

스트리밍 재생목록은 실제 콘텐츠 전체라기보다 여러 미디어 조각의 위치와 재생 순서를 알려주는 인덱스 역할을 할 수 있다. 서버는 원본 재생목록을 가져와 내부 상대 경로를 클라이언트가 접근 가능한 URL로 가공한 뒤 반환할 수 있다.

전체 흐름을 일반화하면 다음과 같다.

`클라이언트 → API 인증 → API 서버 → 원본 재생목록 조회 → 내부 리소스 주소 가공 → 재생목록 반환 → 클라이언트가 CDN에서 실제 조각 수신`

## 서명 URL

보호된 CDN 리소스를 단순 공개 URL로 제공하는 대신, 서버가 리소스 식별 정보와 만료 조건 등을 기반으로 검증값을 생성해 URL에 붙이는 방식이 사용될 수 있다. CDN은 요청을 받을 때 만료 조건과 검증값을 확인한 뒤 리소스를 제공한다.

중요한 것은 특정 구현의 해시 알고리즘이나 파라미터명이 아니라 다음 보안 속성이다.

- 서명이 어떤 리소스와 조건을 묶는가
- 경로나 만료 조건을 바꾸면 검증이 실패하는가
- URL의 유효기간이 사용 목적에 적절한가
- 발급된 URL을 다른 주체가 재사용할 수 있는가
- 서명 생성에 사용하는 비밀정보가 안전하게 관리되는가

요청 HMAC과 CDN URL 서명은 모두 검증값을 사용한다는 점에서는 닮았지만 동일한 프로토콜이라고 가정하면 안 된다. 실제 알고리즘과 검증 규칙은 각각의 구현을 확인해야 한다.

## 저장 경로와 외부 URL 분리

DB에는 환경에 독립적인 리소스 경로만 저장하고, 애플리케이션이 설정된 base URL과 접근 조건을 결합해 외부 URL을 만들 수 있다. 이렇게 하면 외부 호스트나 전달 환경의 변경을 데이터 전체 수정과 분리할 수 있다.

## 보안 연결

진단에서는 정상 앱의 동작을 복제하는 데 그치지 않고, 허가된 환경에서 다음 경계를 확인한다.

- 리소스 식별자를 변경했을 때 권한 밖 콘텐츠가 발급되는가
- 만료된 URL이 실제로 거절되는가
- 서명에 포함된 리소스 조건을 변경했을 때 검증이 실패하는가
- 발급된 URL의 재사용 범위가 설계 의도와 일치하는가
- API 인증을 우회하는 별도 원본 접근 경로가 존재하는가

문서에 구조가 있다는 사실만으로 취약점을 판정하지 않고 실제 권한 모델과 구현을 함께 검증한다.

## 결론

콘텐츠 전달 구조는 `API의 인증·권한 판단`과 `CDN의 실제 바이트 전송`을 분리해서 읽는다. 서명 URL은 접근을 제한하는 하나의 수단이며 안전성은 서명 대상, 만료, 재사용 범위, 비밀정보 관리와 실제 검증 구현을 함께 봐야 판단할 수 있다.
