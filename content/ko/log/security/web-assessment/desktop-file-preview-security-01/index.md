## 1. 학습 목표

설치형 파일 뷰어를 "데이터를 저장하지 않는 읽기 전용 앱"이 아니라 **신뢰할 수 없는 파일을 parser와 renderer에 전달하는 프로그램**으로 이해한다.

```text
untrusted file
    ↓
format parser / decoder
    ↓
normalized representation
    ↓
renderer
    ↓
화면
```

보안 점검의 핵심은 이 흐름에서 입력이 어디까지 도달하고, 각 단계가 어떤 권한을 가지며, 실패했을 때 피해가 어디까지 확장되는지를 확인하는 것이다.

## 2. 신뢰 경계: 읽기 전용도 입력 처리다

파일을 수정하거나 실행하지 않더라도 앱은 파일의 구조를 해석한다. 문서 parser는 텍스트를 다른 표현으로 변환할 수 있고, 이미지 decoder는 압축된 바이트를 픽셀로 복원하며, 압축 parser는 내부 entry와 경로를 해석한다.

따라서 "보기만 한다"는 것은 "처리하지 않는다"는 뜻이 아니다.

> 읽는다 → 파싱한다 → 파서와 렌더러의 공격 표면에 입력이 들어간다.

계정·서버·DB가 없는 앱에서도 이 경계는 존재한다.

## 3. 포맷보다 취약점 유형으로 보는 이유

지원 포맷을 하나씩 나열하는 방식만으로는 같은 구현 결함을 반복해서 놓칠 수 있다. 먼저 취약점 유형을 기준으로 대표 입력을 고르고, 동일한 처리 계열의 다른 포맷으로 범위를 확장하는 편이 구조를 이해하기 쉽다.

| 입력 계열 | 먼저 볼 위험 |
| --- | --- |
| HTML로 변환되는 문서 | 스크립트·마크업 주입, sanitizer 우회 |
| XML 계열 | 외부 참조, parser 설정 |
| 압축 | 경로 경계, 자원 상한 |
| 이미지·미디어 | decoder 오류, 자원 고갈 |
| 링크·경로 | canonicalization, 허용 범위 이탈 |

이 표는 특정 제품의 지원 포맷을 뜻하지 않는다. **어떤 종류의 parser가 존재하는지 확인한 뒤 해당되는 행만 적용**한다.

## 4. 문서·웹 콘텐츠 렌더링

문서 입력을 HTML 같은 웹 표현으로 바꿔 WebView에 삽입하는 구조라면 변환과 렌더링 사이의 신뢰 경계를 본다.

핵심 질문은 다음과 같다.

- 생성된 마크업을 DOM에 넣기 전에 sanitizer가 적용되는가
- event handler나 scriptable URL처럼 실행 의미를 갖는 속성을 제한하는가
- SVG처럼 문서와 이미지의 성격을 함께 가진 포맷을 별도로 다루는가
- 신뢰할 수 없는 렌더 결과가 앱의 네이티브 bridge에 접근할 수 있는가
- CSP 같은 브라우저 정책이 보조 방어로 적용되는가

여기서 중요한 것은 XSS 자체보다 **XSS 이후 권한**이다. WebView 안의 스크립트 실행이 곧 OS 코드 실행을 뜻하지는 않는다. 실제 위험도는 해당 renderer가 가진 네이티브 capability와 격리 수준에 의해 결정된다.

## 5. XML 계열 입력과 외부 참조

HTML의 문자 참조와 XML의 entity는 같은 단어가 등장하지만 보안 의미가 다르다. HTML에서 특수문자를 문자 참조로 바꾸는 것은 출력 무해화에 쓰일 수 있지만, XML entity는 parser가 값을 치환하는 문법 기능이다.

XML parser가 외부 entity나 외부 resource 해석을 허용하면 로컬 파일 또는 네트워크 resource 접근으로 이어질 수 있다. 따라서 XML 기반 입력에서는 **외부 entity·DTD·외부 resource resolution이 기본적으로 비활성인지**를 확인한다.

## 6. 압축 파일과 경로 경계

압축 entry에는 파일명뿐 아니라 경로가 포함될 수 있다. 추출 기능이 있다면 entry 경로를 그대로 목적 경로와 결합하지 않고, 최종 경로를 정규화한 뒤 허용된 추출 root 안에 남는지 확인해야 한다.

뷰어가 실제 추출 없이 목록만 보여준다면 임의 파일 쓰기 공격면은 줄어든다. 이때는 기능을 추정하지 말고 다음 사실을 확인한다.

- 미리보기 과정에서 임시 파일을 생성하는가
- entry 경로를 표시하거나 처리할 때 정규화가 일어나는가
- 압축 해제 크기·entry 수·중첩 깊이 같은 자원 상한이 있는가

압축률이 매우 높은 입력은 CPU·메모리·디스크를 고갈시킬 수 있으므로 **기능적 경로 검증과 자원 제한을 별개의 문제**로 본다.

## 7. 이미지·미디어와 네이티브 decoder

이미지나 미디어는 스크립트가 없어도 안전하다고 단정할 수 없다. decoder가 길이·크기·offset 같은 메타데이터를 잘못 처리하면 crash나 메모리 안전 문제로 이어질 수 있다.

다만 소수의 손상 표본이 정상 처리됐다는 사실은 decoder 전체의 메모리 안전성을 증명하지 않는다. 이런 결함의 체계적 발견에는 fuzzing 같은 별도 방법론이 필요하다.

따라서 제한된 수동 점검에서는 다음처럼 결과 범위를 명확히 남긴다.

```text
관찰된 표본에서 crash 없음
≠
decoder 메모리 안전성 검증 완료
```

거대한 미디어 입력도 별도의 공격면이다. 전체 파일을 한 번에 메모리에 적재하거나 크기 상한 없이 decode한다면 로컬 입력만으로도 서비스 거부 상태가 발생할 수 있다.

## 8. 파일 스코프와 링크 해석

"허용된 폴더 아래의 파일만 읽는다"는 정책은 문자열 경로 비교만으로 충분하지 않다. 심볼릭 링크, 상대경로, mount/reparse 계열 기능 등으로 논리 경로와 실제 대상이 달라질 수 있기 때문이다.

안전한 검증의 핵심은 **최종 대상 경로를 canonicalize한 뒤 허용 root와 다시 비교하는 것**이다. 경로 확인과 실제 파일 열기 사이에 대상이 바뀔 수 있는 경쟁조건도 구현에 따라 고려해야 한다.

## 9. 플랫폼별 렌더링 경계

독립 실행형 앱과 OS가 제공하는 미리보기 확장은 같은 파일을 그리더라도 실행 컨텍스트가 다를 수 있다. 어떤 플랫폼에서는 앱 자체 renderer가 파일을 처리하고, 다른 플랫폼에서는 OS가 확장 모듈을 별도 프로세스에서 호출할 수 있다.

따라서 한 플랫폼의 결과를 다른 플랫폼에 일반화하지 않는다. 확인할 것은 제품명이 아니라 다음 세 가지다.

1. 파일을 실제로 파싱하는 프로세스가 무엇인가
2. 그 프로세스의 sandbox와 파일·네트워크 권한은 무엇인가
3. crash·cache·임시파일이 어느 경계에 남는가

시험 장비나 실행 환경이 없다면 해당 플랫폼은 판정하지 않고 데이터 부족으로 남긴다.

## 10. 공격자·방어자 관점

공격자는 "어떤 확장자를 지원하는가"보다 **같은 입력이 어느 parser를 거쳐 어떤 권한으로 렌더되는가**를 본다. 하나의 파일이 parser → WebView → native bridge처럼 여러 경계를 연속으로 통과한다면 각 단계의 실패가 결합될 수 있다.

방어자는 입력 검증 하나에 의존하지 않는다. parser의 안전한 설정, sanitizer, renderer 격리, 최소 capability, 경로 canonicalization, 자원 상한을 겹쳐서 적용한다.

## 11. 검증 포인트

허가된 격리 환경에서는 파괴적인 exploit 대신 결과가 제한된 probe를 사용한다.

```text
목표
→ 신뢰할 수 없는 파일의 처리 경계 확인

구성 요소
→ parser / decoder / renderer / filesystem / native bridge

연결 구조
→ file → parser → renderer → privileged capability

검증 포인트
→ 실행 의미 차단 / 경로 범위 / crash / 자원 상한 / 외부 연결

기록 포맷
→ 입력 조건 / 관찰 사실 / 증적 / 미검증 범위 / 다음 확인
```
