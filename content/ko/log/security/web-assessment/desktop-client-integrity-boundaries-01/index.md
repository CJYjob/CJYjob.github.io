## 1. 학습 목표

설치형 클라이언트의 보안을 "바이너리가 난독화되어 있는가" 하나로 판단하지 않고, **어떤 코드가 신뢰되는가 → 어떤 경로에서 추가 코드가 로드되는가 → 어느 권한으로 실행되는가 → 변조를 어떻게 검증하는가** 순서로 본다.

## 2. 코드 서명과 런타임 무결성

코드 서명은 배포된 바이너리의 발행 주체와 서명 이후 변조 여부를 검증하는 수단이다. 개발 단계의 미서명 빌드는 최종 배포 상태와 다를 수 있으므로, "출시 시 적용 예정"이라는 진술만으로 최종 판정을 내리지 않고 실제 배포 후보에서 다시 확인한다.

코드 서명과 애플리케이션의 자기무결성 검사는 목적이 겹치지만 동일하지 않다. 전자는 OS·배포 체계가 서명을 검증하는 것이고, 후자는 앱이 실행 중 자신의 구성요소나 중요 resource의 기대 상태를 별도로 확인하는 방식이다.

따라서 단순히 파일을 변조했을 때 실행된다는 사실만으로 모든 환경에서 취약하다고 단정하기보다 **어떤 신뢰 모델을 요구하는 제품인지와 OS의 서명 검증 경로**를 함께 본다.

## 3. 배포 형태와 역분석 가능성

AOT, JIT, 중간 표현, native code는 실행 시점과 배포물에 남는 정보가 다르다. 그러나 `AOT = 이름이 모두 사라짐`, `JIT = 거의 원본 소스 복원`처럼 절대화하면 안 된다. 심벌, reflection metadata, 문자열, debug 정보, 최적화 수준, 패키징 방식에 따라 역분석에 남는 정보가 달라진다.

난독화는 분석 비용을 높이는 보조 통제다. 원래 식별자가 제거된 경우 분석 도구나 AI가 기능을 추정해 새 이름을 제안할 수는 있지만, 삭제된 원래 이름을 사실로 복원한다고 볼 수는 없다.

점검에서는 기술 이름보다 실제 릴리스 산출물을 본다.

- debug symbol·source map·개발용 metadata가 배포물에 포함되는가
- 함수·타입·경로·endpoint 등 불필요한 내부 정보가 얼마나 남는가
- 난독화가 필요한 위협 모델이라면 실제 릴리스 빌드에 적용되는가
- 심벌 파일이 운영 배포물과 분리되어 관리되는가

## 4. 동적 라이브러리 로딩 경계

네이티브 애플리케이션은 실행 중 여러 동적 라이브러리를 로드한다. 라이브러리 이름만 지정하고 검색 경로가 공격자가 쓸 수 있는 위치까지 포함된다면 의도하지 않은 라이브러리가 먼저 선택될 위험이 있다.

핵심 질문은 다음과 같다.

- 라이브러리 경로가 명확하게 고정되어 있는가
- 검색 대상 디렉터리에 일반 사용자가 쓸 수 있는가
- 로드 대상의 서명·무결성을 검증하는가
- 설치 위치와 임시 위치의 ACL이 적절한가

즉 문제의 본질은 특정 파일명 자체가 아니라 **검색 순서와 쓰기 권한이 만나는 지점**이다.

## 5. 설치·제거 과정의 권한 경계

설치·업데이트·제거 프로그램은 일반 앱보다 높은 권한으로 동작할 수 있다. 높은 권한 프로세스가 일반 사용자가 수정할 수 있는 임시 파일이나 라이브러리를 신뢰하면 낮은 권한 사용자가 그 경계를 이용할 수 있다.

이런 문제에서는 "악성 코드가 이미 실행 중인데 무슨 의미가 있는가"보다 **어느 권한에서 어느 권한으로 넘어가는가**를 본다. 일반 사용자 컨텍스트에서 시작한 코드가 관리자 컨텍스트의 프로세스에 영향을 줄 수 있다면 권한 상승 문제가 된다.

임시 파일 생성과 사용 사이의 시간차가 있다면 경쟁조건도 고려한다. 방어는 안전한 임시 디렉터리, 예측 불가능하고 배타적인 파일 생성, ACL, 검증된 코드 로딩 등으로 구성한다.

## 6. 디버깅 방어와 릴리스 빌드 위생

안티디버깅은 분석 비용을 높이는 보조 통제다. 운영체제가 제공하는 debugger 상태 확인, timing 차이, process metadata 등을 이용할 수 있지만 우회 가능성이 존재한다.

따라서 "디버거가 붙는다"는 사실을 곧바로 원격 코드 실행이나 권한 상승과 동일시하지 않는다. 점검에서는 다음을 분리한다.

```text
디버깅 가능 여부
→ 분석 저항성

민감정보가 메모리에 평문으로 남는가
→ 정보 노출 가능성

디버깅을 통해 보안 결정을 변조할 수 있는가
→ 실제 보안 통제 우회 가능성
```

릴리스 빌드에서는 디버그 전용 기능과 상세 로그가 실제 산출물에서 제거되거나 안전하게 비활성화되는지 확인한다. 단순한 UI 플래그로 숨겨져 있을 뿐 호출 가능한 코드가 남는지, 로그 레벨과 무관하게 민감 본문이 기록되는 경로가 없는지도 별도로 본다.

## 7. 메모리와 crash dump

미리 본 문서나 자격정보가 메모리에 존재하는 것은 처리 과정에서 불가피할 수 있다. 보안 질문은 **필요 이상 오래 남는가, crash dump나 swap 같은 2차 저장물로 확산되는가, 다른 낮은 권한 주체가 접근 가능한가**이다.

따라서 단순 문자열 발견보다 데이터 수명과 접근 권한을 함께 기록한다.

## 8. 공격자·방어자 관점

공격자는 서명된 메인 실행 파일만 보지 않고, 그 파일이 이후 신뢰하는 라이브러리·업데이트·임시 파일·IPC를 추적한다. 방어자는 신뢰 사슬 전체에서 쓰기 가능한 경로와 높은 권한 실행이 만나는 곳을 제거한다.

## 9. 검증 포인트

허가된 사본과 격리 환경에서 다음 사실을 수집한다.

- 배포 후보의 실제 코드 서명 상태
- 실행 파일과 라이브러리의 로딩 경로
- 설치 디렉터리·임시 디렉터리의 쓰기 권한
- 보안 통제의 디버깅 의존 여부
- debug symbol·상세 로그·개발 기능의 릴리스 포함 여부
- 민감 데이터의 메모리·dump 잔존 범위
