## 1. 학습 목표

중앙 서버 없이 같은 근거리망의 기기끼리 데이터를 주고받는 설치형 애플리케이션을 **네트워크 보안과 클라이언트 보안이 만나는 대상**으로 이해한다.

핵심 흐름은 다음과 같다.

```text
발견
→ 최초 신뢰 형성
→ 상호 인증
→ 암호화된 전송
→ 수신 endpoint의 입력 처리
→ 로컬 저장·사용
```

각 단계가 서로 다른 보장을 제공하므로 하나의 통제로 전체 안전성을 설명하지 않는다.

## 2. 공격면의 이동

로컬 파일 뷰어에서는 신뢰할 수 없는 파일이 parser에 들어가는 경계가 중심이었다. P2P 동기화 앱에서는 같은 LAN의 다른 노드가 직접 입력을 보낼 수 있으므로 공격면이 네트워크 프로토콜까지 확장된다.

주요 질문은 다음과 같다.

- 미신뢰 노드가 수신 서비스에 접근할 수 있는가
- 정상 노드를 사칭해 신뢰 관계를 만들 수 있는가
- 전송 중 내용을 관찰하거나 변조할 수 있는가
- 과거의 정상 메시지를 다시 사용할 수 있는가
- 인증을 통과한 입력이 parser·filesystem 같은 후속 경계에서 안전하게 처리되는가

## 3. 발견은 인증이 아니다

근거리 서비스 발견에는 UDP multicast나 broadcast 계열 방식이 사용될 수 있다. 멀티캐스트의 전달 범위는 TTL뿐 아니라 네트워크 구성과 라우터의 multicast forwarding 정책에 영향을 받으므로, **TTL 값 하나만으로 항상 동일한 LAN 경계를 보장한다고 단정하지 않는다.**

더 중요한 원칙은 발견과 인증을 분리하는 것이다.

```text
발견
= 통신 가능한 후보를 찾음

인증
= 그 후보가 이전에 신뢰한 주체인지 확인
```

따라서 공격자가 발견 메시지를 흉내 낼 수 있더라도 그것만으로 신뢰 관계가 형성되어서는 안 된다.

## 4. CA 신뢰와 피닝 기반 신뢰

일반적인 공개 HTTPS는 서버 인증서가 신뢰된 CA 체인과 기대한 이름에 연결되는지를 검증한다. 반면 폐쇄적인 기기 간 통신에서는 외부 CA 대신 **페어링 과정에서 교환한 공개키 또는 인증서 지문을 이후 신뢰 기준으로 고정**하는 설계를 사용할 수 있다.

상호 TLS를 사용하면 양쪽이 각각 인증서를 제시하고 자신의 private key를 보유하고 있음을 핸드셰이크에서 증명한다. 하지만 `mTLS를 사용한다`는 사실만으로 안전성을 판정할 수 없다. 핵심은 **어떤 인증서를 신뢰하도록 구성했는가**이다.

## 5. TLS에서 인증서와 키 소유 증명

인증서는 공개키와 신원 관련 정보를 서명된 형태로 묶는다. 인증서의 공개키를 아는 것과 그에 대응하는 private key를 가진 것은 다르다.

TLS 핸드셰이크에서는 인증서 검증과 함께 프로토콜에 정의된 서명·키 교환 절차를 통해 상대가 해당 private key를 실제로 사용할 수 있는지 확인한다. 따라서 공개 인증서를 복사하는 것만으로 정상 상대를 그대로 사칭할 수는 없다.

피닝을 사용한다면 별도의 질문이 추가된다.

- 무엇을 pinning하는가: 전체 인증서, 공개키, 지문 등
- 인증서 갱신·기기 재등록 시 pin을 어떻게 바꾸는가
- pin 불일치가 fail closed 되는가
- OS trust store의 추가 CA가 이 검증을 우회할 수 있는가

## 6. 세션 MITM과 최초 페어링

정상적으로 고정된 공개키·인증서와 private key 소유 증명이 결합되면 이후 세션의 중간자 공격 난도는 크게 올라간다. 하지만 이를 `MITM이 불가능하다`고 절대화하지 않는다. 구현 결함, 검증 비활성화, 키 탈취, 잘못된 재등록 절차 같은 다른 경로가 남을 수 있다.

TOFU(Trust On First Use) 방식이라면 특히 **최초 신뢰를 고정하는 순간**을 별도의 공격면으로 본다. 아직 기대하는 상대 키가 없는 상태에서 공격자의 키를 정상 상대의 것으로 저장하면 이후 암호화가 정상이어도 잘못된 상대를 안전하게 인증하는 결과가 된다.

따라서 페어링에서는 다음을 본다.

- 사용자가 두 기기의 신원을 신뢰 가능한 채널로 비교할 수 있는가
- 짧은 코드라면 시도 횟수와 유효 시간이 제한되는가
- 페어링 요청이 명시적인 사용자 동작 없이 완료되지 않는가
- 기존 신원을 교체하거나 재등록할 때 기존 신뢰를 우회하지 않는가
- 페어링 해제 후 과거 자격정보가 다시 사용되지 않는가

## 7. 전송 프로토콜과 replay 방어

일부 P2P 프로토콜은 메타데이터를 먼저 보내고 수신 측이 일회성 전송 권한이나 세션 식별자를 발급한 뒤 본문을 받는 구조를 사용할 수 있다. 이 경우 점검에서는 **토큰의 일회성·수명·요청 바인딩**을 확인한다.

TLS 레코드 계층은 활성 연결 안에서 레코드의 순서와 무결성을 보호하지만, 이것만으로 **애플리케이션 요청을 새 연결에서 다시 보내는 replay까지 일반적으로 해결한다고 보지 않는다.** 애플리케이션 수준 replay 방어가 필요하다면 nonce, timestamp, 일회성 토큰, 상태 전이 등 해당 프로토콜의 의미에 맞는 통제가 필요하다.

수신 endpoint에서는 인증 뒤에도 크기 제한, 스키마 검증, parser 오류 처리, 자원 상한을 별도로 확인한다.

## 8. 파일 수신: 취약점과 잔여위험

임의 파일 전송이 제품의 정상 기능이라면 `악성 파일을 저장할 수 있다`는 사실만으로 취약점이 되지는 않는다. 판단에는 신뢰 경계와 후속 동작이 필요하다.

```text
신뢰한 상대가 명시적으로 파일을 전송
+ 자동 실행 없음
→ 기능에 수반되는 잔여위험일 수 있음

미신뢰 상대가 인증을 우회해 파일을 저장
또는 수신 파일이 자동 실행·특권 처리됨
→ 별도의 보안 결함 가능성
```

확장자 경고, 저장 위치 통제, 후속 실행 전 확인 같은 완화책은 잔여위험을 줄일 수 있다. 단, 파일을 실제로 미리보기·파싱한다면 네트워크 인증과 별개로 파일 parser 공격면이 다시 생긴다.

## 9. 무계정 환경의 인증·인가

계정이 없는 설계에서는 기기 키와 페어링 관계가 주체 인증 역할을 할 수 있다. 이때 전통적인 비밀번호 정책을 기계적으로 적용하기보다 실제 신뢰 모델에 맞춰 점검한다.

- 모든 보호 endpoint가 페어링된 기기만 허용하는가
- 기기별 권한 차이가 있다면 서버 측에서 강제되는가
- 신원 키를 교체·폐기할 수 있는가
- 민감 데이터 열람에 OS의 사용자 인증을 추가로 요구하는가

`무계정 = 인증 없음`도 아니고 `mTLS = 인가 완료`도 아니다. 인증된 기기가 어떤 기능을 사용할 수 있는지는 별도의 인가 문제다.

## 10. 격리 시험 환경

P2P 검증은 최소 두 노드가 서로 직접 통신할 수 있는 네트워크가 필요하다. VM의 NAT·bridged·host-only/internal network는 하이퍼바이저와 호스트 구성에 따라 multicast와 inbound 연결 지원이 다를 수 있으므로 **네트워크 모드 이름만으로 동작을 단정하지 않고 실제 패킷 도달성을 확인**한다.

물리 운영망과 분리된 가상 네트워크를 우선하고, 복제한 VM을 사용한다면 앱의 기기 신원·키까지 복제되지 않았는지 확인한다. 두 노드는 서로 다른 신원을 가져야 페어링과 상호 인증을 정상적으로 검증할 수 있다.

## 11. 공격자·방어자 관점

공격자는 발견 메시지보다 **신뢰가 생성·갱신·폐기되는 순간**을 찾는다. 또한 인증 이후 endpoint가 과대 payload나 기형 입력을 어떻게 처리하는지 확인한다.

방어자는 발견을 신뢰하지 않고, 페어링에서 신원을 명시적으로 확인하며, 이후 통신에서 고정된 신원과 키 소유를 검증한다. 그리고 네트워크 인증을 통과한 데이터도 여전히 신뢰할 수 없는 입력으로 취급해 parser·filesystem·UI 경계에서 다시 검증한다.

## 12. 검증 포인트

허가된 격리 환경에서는 다음 흐름으로 증적을 수집한다.

```text
목표
→ P2P 신뢰 경계와 인증 우회 가능성 확인

구성 요소
→ discovery / pairing / TLS identity / receive endpoint / local storage

연결 구조
→ nearby node → discovery → pairing → authenticated channel → parser/storage

검증 포인트
→ 미페어링 접근 거부 / 잘못된 peer 인증서 거부 / 페어링 만료·횟수 제한 /
   신원 재등록 / replay 통제 / 크기·스키마 제한 / 오류 정보 노출

기록
→ 사전 조건 / 관찰 사실 / 증적 / 미검증 범위 / 다음 확인
```
