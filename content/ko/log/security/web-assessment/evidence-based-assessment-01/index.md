## 1. 학습 목표

보안 점검에서 개발자나 운영자의 설명을 무시하지 않되, 설명 자체를 최종 증적으로 취급하지 않는 습관을 만든다.

핵심 흐름은 다음과 같다.

```text
통제에 대한 진술
→ 검증 가능한 가설로 변환
→ 정적 또는 능동 증적 수집
→ 관찰 사실 기록
→ 기준과 대조
→ 판정
```

## 2. 진술과 증적의 차이

"외부 통신이 없다", "위험한 포맷은 차단한다", "격리가 적용되어 있다" 같은 설명은 점검 범위를 정하는 데 유용하지만 그 자체로 구현 상태를 증명하지는 않는다.

각 진술은 관찰 가능한 질문으로 바꾼다.

| 진술 | 증적으로 바꾼 질문 |
| --- | --- |
| 외부 통신 없음 | 실행 중 실제 socket·network event가 발생하는가 |
| 특정 입력 차단 | 해당 입력이 모든 관련 경로에서 거부되는가 |
| 격리 적용 | 신뢰할 수 없는 renderer가 privileged capability에 도달하지 못하는가 |
| 자격정보 저장 없음 | 설정·로그·로컬 저장소에 재사용 가능한 secret이 존재하는가 |

## 3. 정적 수집과 능동 시험

### 정적 수집

앱을 실행하지 않고 배포 산출물과 구성에서 확인할 수 있는 사실을 수집한다.

예를 들어 코드 서명 상태, 바이너리 완화 설정, debug symbol·source map·개발용 endpoint 흔적, 의존성 고지, 로컬 설정 구조 등을 확인할 수 있다.

### 능동 시험

허가된 격리 환경에서 앱을 실제 실행하고 통제된 입력을 전달해 동작을 관찰한다. 렌더 성공·거부·crash, 파일 생성, 네트워크 연결, 권한 없는 기능 호출의 거부 여부 등이 관찰 대상이다.

정적 결과와 능동 결과가 서로 보완되어야 한다. 설정에 통제가 존재해도 실행 경로에서 적용되지 않을 수 있고, 능동 표본이 정상이어도 모든 코드 경로를 증명하지는 못한다.

## 4. 비파괴 probe의 역할

점검용 입력은 목표한 통제를 관찰하는 데 필요한 최소 자극이어야 한다. 실제 피해를 만드는 exploit보다 **결과가 제한되고 되돌릴 수 있는 probe**를 우선한다.

예를 들어 경로 경계를 확인한다면 운영체제의 민감 파일을 목표로 하지 않고 격리된 테스트 디렉터리의 marker를 사용한다. 자원 상한을 확인할 때도 시스템 장애를 목표로 하지 않고 사전에 정한 CPU·메모리·시간 한도 안에서 중단한다.

이렇게 하면 "통제가 작동하는가"라는 질문과 "실제 피해를 얼마나 크게 만들 수 있는가"라는 질문을 분리할 수 있다.

## 5. SBOM과 의존성 매핑

SBOM(Software Bill of Materials)은 제품에 포함된 소프트웨어 구성요소와 버전을 식별하기 위한 자료다. 알려진 취약점을 제품에 정확히 매핑하려면 이름만 아니라 **실제 포함 버전과 사용 여부**가 필요하다.

SBOM이 없다면 배포물의 의존성 고지, package metadata, binary metadata 등으로 보완할 수 있지만, 근거 수준이 낮아질 수 있다. 따라서 CVE 매핑 결과에는 확정·추정의 근거 수준을 함께 남긴다.

## 6. N/A·양호·판정불가를 구분하기

세 상태를 섞지 않는다.

- **N/A**: 해당 기능이나 공격면이 존재하지 않는다는 근거가 있다.
- **양호**: 공격면이 존재하며 요구 통제가 증적으로 확인되었다.
- **판정불가**: 공격면은 존재하거나 존재 가능하지만 장비·범위·자료 부족으로 필요한 검증을 하지 못했다.

"시험하지 않았다"는 사실을 양호로 바꾸지 않는 것이 중요하다.

## 7. 기록 포맷

각 시험은 다음 형식으로 남기면 재현성과 검토 가능성이 높아진다.

```text
목표
구성 요소
연결 구조
사전 조건
입력 / probe
관찰 사실
증적 위치
성공 여부
막힌 지점
원인 추정
미검증 범위
다음 시도
자산화 포인트
```

판정과 관찰을 분리하면 나중에 기준이 바뀌거나 추가 증적이 들어와도 다시 해석하기 쉽다.

## 8. 공격자·방어자 관점

공격자는 문서화된 통제보다 실제 실행 경로의 차이를 찾는다. 방어자와 점검자는 통제의 존재를 문서가 아니라 재현 가능한 증적으로 확인한다.

이 방법은 데스크톱 앱뿐 아니라 웹·API·인프라 점검에도 그대로 적용할 수 있다.
