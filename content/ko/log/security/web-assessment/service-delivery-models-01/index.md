## 학습 목적

같은 "웹 취약점 점검"이라도 대상이 전통적인 웹 애플리케이션인지, API인지, 위젯인지, 설치형 클라이언트인지에 따라 실제 공격면이 달라진다. 체크리스트를 기계적으로 적용하기 전에 **서비스가 어떤 형태로 제공되는지 판별하고, 그 형태가 만드는 신뢰 경계와 공격면을 먼저 찾는 것**을 목표로 한다.

핵심 흐름은 다음과 같다.

`제공 형태 판별 → 실제 공격면 식별 → 적합한 점검 기준 선택 → 취약/양호/N/A 판정`

## 1. 전통 서버 렌더링 웹앱

서버가 HTML 페이지를 만들어 내려주고 로그인, 세션, 폼 제출을 중심으로 상호작용하는 형태다. 전통적인 웹 취약점 체크리스트가 가장 직접적으로 적용된다.

주요 공격면은 입력값을 통한 SQL Injection·XSS·명령어 실행, 세션 쿠키 관리, CSRF, 인증·인가, 파일 업로드·다운로드, 오류 정보 노출 등이다.

점검에서는 폼뿐 아니라 URL, 헤더, 쿠키 등 서버 처리에 영향을 주는 입력을 함께 추적하고, 상태 변경 요청과 세션 경계를 확인한다.

## 2. SPA와 백엔드 API

SPA(Single-Page Application)는 브라우저의 JavaScript가 화면을 구성하고 백엔드 API에서 데이터를 받아오는 형태다. 프론트엔드와 API를 서로 다른 공격면으로 나누어 봐야 한다.

프론트에서는 DOM 기반 XSS, 신뢰할 수 없는 입력 source와 위험한 sink, 브라우저 저장소의 토큰, 번들·소스맵의 민감정보 노출 등을 본다. 백엔드에서는 UI에서 버튼을 숨겼다는 사실을 신뢰하지 않고 API를 직접 호출해 인증과 인가를 다시 검증한다.

즉 **클라이언트의 UI 통제와 서버의 권한 통제는 별개**다.

## 3. API-only·Headless 서비스

화면 없이 API 자체를 외부 소비자에게 제공하는 형태다. 이 경우 API 명세가 공개되어 있다는 사실만으로 취약점이라고 판단할 수 없다. 공개가 제품 기능일 수 있기 때문이다.

점검의 중심은 노출 여부보다 **인가 경계**로 이동한다.

- 객체 식별자를 바꾸었을 때 권한 밖 객체에 접근할 수 있는가
- 낮은 권한으로 상위 기능을 호출할 수 있는가
- 응답에 필요 이상의 민감한 속성이 포함되는가
- 요청에 문서화되지 않은 속성을 추가했을 때 권한 관련 상태가 변경되는가
- 호출량·페이로드 크기 등 자원 소비 통제가 있는가
- 토큰이나 요청 서명의 만료·재전송 방어가 적절한가

공개 API가 정상적으로 열리는 것과 공개하면 안 되는 API가 같은 경로로 노출되는 것은 구분해야 한다.

## 4. 임베드 위젯·서드파티 스크립트

다른 웹사이트의 iframe이나 script 안에 삽입되어 동작하는 형태다. 이 유형은 외부 사이트에 포함되는 것이 본래 기능이므로 프레이밍 자체를 무조건 차단하는 권고가 제품 기능과 충돌할 수 있다.

따라서 클릭재킹은 단순히 "프레임에 들어가는가"보다 **프레임 안에서 한 번의 사용자 동작으로 민감한 상태 변경이 가능한가**를 본다. 또한 부모 페이지와 iframe 사이의 `postMessage` origin 검증, 삽입 스크립트 공급망, iframe sandbox, 부모·자식 간 데이터 경계가 중요하다.

## 5. 정적 사이트

서버의 동적 처리 없이 미리 생성된 HTML·CSS·JavaScript를 제공하는 형태다. 로그인, DB, 세션, 업로드 기능 등이 실제로 없다면 관련 취약점은 "양호"가 아니라 **N/A(해당 없음)** 로 분류하는 것이 더 정확하다.

남는 주요 점검 영역은 HTTPS 강제와 HSTS, 설정·백업·소스 파일 노출, 디렉터리 인덱싱, 오류·응답 헤더의 정보 노출, 클라이언트 JavaScript의 DOM XSS 등이다.

중요한 것은 N/A 판정에도 **해당 공격면이 존재하지 않는다는 증적**이 필요하다는 점이다.

## 6. 관리 콘솔·백오피스

운영자나 고객 조직의 직원이 사용하는 관리 UI다. 이름이나 경로가 `/admin`인지보다 실제 접근 통제와 권한 범위가 중요하다.

주요 확인 지점은 외부 도달성, VPN·허용 IP 등 접근 경계, 역할별 기능 수준 인가, 하위 권한 계정의 과도한 기능 접근, 테넌트 간 데이터 격리다. 경로를 숨기는 것은 접근 통제의 대체 수단이 아니다.

## 7. 데스크톱·모바일 네이티브 클라이언트

사용자 기기에 설치되는 실행 파일이나 모바일 앱은 전통적인 웹 체크리스트만으로 충분하지 않다. 바이너리와 로컬 실행환경 자체가 공격면이 된다.

코드 서명과 변조 탐지, 바이너리 보호, 하드코딩 secret, 로컬 자격정보 저장, TLS와 인증서 검증, 딥링크·프로토콜 핸들러, IPC, 업데이트 경로 등을 확인한다. 특히 클라이언트가 보관한 권한·라이선스·카운터 같은 상태를 서버가 그대로 신뢰하는지도 중요하다.

모바일 앱이 백엔드 API를 사용한다면 **네이티브 클라이언트 공격면과 API 공격면을 함께** 봐야 한다.

## 8. WebView를 포함한 하이브리드 클라이언트

네이티브 애플리케이션 안에 브라우저 엔진을 포함해 웹 콘텐츠를 표시하는 형태다. 웹과 네이티브 사이에 JavaScript-native bridge가 존재할 수 있어 두 영역의 취약점이 연결될 수 있다.

웹 입력의 XSS가 브릿지를 거쳐 네이티브 기능 호출로 확대되는지, WebView가 어떤 origin과 URL을 허용하는지, 파일 접근·JavaScript·혼합 콘텐츠 설정은 적절한지, 네이티브와 웹 사이에 전달되는 입력을 검증하는지 확인한다.

## 9. 마이크로서비스·서버 간 API

사용자가 직접 호출하는 것이 아니라 서비스들이 내부에서 서로 호출하는 API다. "내부망이므로 신뢰한다"는 가정이 공격면이 될 수 있다.

서비스 간 인증, 내부 전용 endpoint의 외부 도달성, SSRF를 통한 내부 서비스 접근, 클라우드 메타데이터 접근, 하나의 서비스 침해 이후 측면 이동 가능성을 확인한다.

## 10. Webhook·Callback 수신 endpoint

외부 시스템이 이벤트 발생 시 서버로 HTTP 요청을 보내는 형태다. 공개된 수신 URL 자체보다 **누가 보낸 이벤트인지 검증하고 동일 이벤트의 재사용을 어떻게 통제하는지**가 중요하다.

주요 점검 영역은 요청 서명 검증, timestamp·nonce 등을 이용한 replay 방어, 안전한 payload parsing, 콜백 하나만으로 민감 상태를 확정하지 않고 필요한 경우 서버 측에서 원 시스템의 상태를 재확인하는지 여부다.

## 제공 형태를 판별하기 위한 질문

| 질문 | 우선 검토할 형태 |
| --- | --- |
| 화면 없이 API만 제공되는가? | API-only / Webhook |
| 다른 사이트의 iframe·script에 삽입되는가? | 임베드 위젯 |
| 로그인·입력·DB 같은 동적 기능이 없는가? | 정적 사이트 |
| 운영자나 직원이 사용하는 관리 화면인가? | 관리 콘솔 |
| 설치형 실행 파일이나 모바일 앱인가? | 네이티브 클라이언트 |
| 앱 내부에 WebView가 있는가? | 하이브리드 클라이언트 |
| 서비스끼리 내부에서 호출하는가? | 서버 간 API |

하나의 제품이 반드시 한 형태에만 속하는 것은 아니다. 예를 들어 모바일 앱은 네이티브 클라이언트이면서 API를 사용하고, 일부 화면은 WebView일 수 있다. 따라서 실제 점검에서는 제품 이름 하나를 분류하는 것보다 **구성 요소별 제공 형태와 신뢰 경계를 나누는 것**이 중요하다.

## 기존 학습과의 연결

기존의 모바일 API 점검 준비에서는 점검 환경, 앱 자산, 인증정보, 권한 모델과 정상 요청 기준선을 먼저 확보하는 절차를 정리했다. 이번 학습은 그보다 한 단계 앞에서 **대상의 제공 형태가 무엇인지 판단해야 적용할 점검 기준과 N/A 범위를 제대로 정할 수 있다**는 관점을 추가한다.

## 보안 점검 프레임

서비스를 처음 받았을 때 체크리스트부터 펼치지 않는다.

1. 사용자가 실제로 접하는 제공 형태를 확인한다.
2. 브라우저, 앱, API, 서버 간 통신 등 구성 요소를 분리한다.
3. 각 구성 요소 사이의 신뢰 경계를 그린다.
4. 외부 입력이 어디까지 도달하는지 추적한다.
5. 인증·인가·상태 변경·민감정보 처리 지점을 찾는다.
6. 실제 존재하는 공격면에 맞는 기준을 선택한다.
7. 존재하지 않는 공격면은 근거를 남기고 N/A로 분류한다.
8. 정상 동작 기준선을 확보한 뒤 변조와 우회 검증을 수행한다.

## 현재 상태

제공 형태별 공격면과 점검 기준을 분리하는 관점을 정리한 중간 학습 기록이다. 이후 실제 허가된 점검 대상에서 `형태 판별 → 공격면 식별 → 기준 매핑 → 정상 기준선 → 검증 → 판정` 흐름을 적용하고 결과를 보완한다.
