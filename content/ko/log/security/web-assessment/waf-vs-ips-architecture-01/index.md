## 1. 학습 목표

WAF(Web Application Firewall)와 IPS(Intrusion Prevention System)를 단순히 "WAF는 L7, IPS는 L3/L4"처럼 외우지 않고, **무엇을 파싱하고 어떤 문맥으로 정상·공격을 판정하는가**를 기준으로 이해한다.

핵심 질문은 다음과 같다.

> IPS도 애플리케이션 계층 프로토콜을 분석할 수 있는데, 왜 웹 애플리케이션을 위해 별도의 WAF가 필요한가?

이번 학습에서는 그 답을 `관측 범위 → 파싱 → 정규화 → 탐지 모델 → 상태 → 한계` 순서로 정리한다.

## 2. WAF와 IPS를 계층만으로 구분하면 안 되는 이유

WAF는 주로 HTTP/HTTPS라는 좁은 영역을 깊게 해석한다. URI, HTTP method, header, cookie, query parameter, form body, JSON/XML/multipart 같은 웹 요청 구조를 애플리케이션 관점에서 나눈다.

IPS는 더 넓은 네트워크·프로토콜 범위를 다룬다. 제품에 따라 DPI(Deep Packet Inspection)를 이용해 HTTP를 포함한 여러 애플리케이션 프로토콜을 해석할 수 있으므로 "IPS는 L7을 못 본다"고 말하면 정확하지 않다.

둘의 차이는 단순한 OSI 계층보다 **탐지에 사용하는 문맥의 깊이와 목적**에서 보는 것이 낫다.

```text
IPS 관점
이 스트림에서 알려진 공격 특성이나 비정상 프로토콜 패턴이 보이는가?

WAF 관점
이 HTTP 요청의 특정 파라미터·세션·endpoint 문맥에서 이 값과 동작이 허용되는가?
```

즉 IPS는 여러 프로토콜에 걸쳐 넓은 공격면을 담당하고, WAF는 웹 요청 구조를 더 세밀한 변수와 애플리케이션 문맥으로 분석한다.

## 3. 시그니처만으로 웹 공격을 막기 어려운 이유

### 3.1 같은 의미를 여러 표현으로 만들 수 있다

HTTP와 애플리케이션 입력은 percent encoding, 문자 표현, 대소문자, 주석, 공백 등 여러 표현을 가질 수 있다. 원본 문자열만 비교하면 논리적으로 같은 입력이 다른 바이트열로 보일 수 있다.

따라서 탐지 전에 **정규화(normalization)** 가 필요하다.

### 3.2 같은 문자열도 위치에 따라 의미가 달라진다

어떤 문자열이 자유 형식 게시글 본문에 존재하는 것과 숫자 식별자 필드에 존재하는 것은 의미가 다르다. WAF는 단순히 "문자열이 존재하는가"뿐 아니라 **어느 변수에서 관측되었는가**를 활용할 수 있다.

### 3.3 문법적으로 정상인 공격도 있다

IDOR/BOLA처럼 다른 객체의 식별자로 바꾸어 접근하는 공격은 HTTP나 JSON 문법만 보면 완전히 정상일 수 있다.

```text
정상 사용자 요청과 공격 요청의 차이
= 문자열 형태가 아니라 "이 사용자가 이 객체에 접근할 권한이 있는가"
```

따라서 WAF의 깊은 HTTP 이해에도 한계가 있다. 애플리케이션 내부의 실제 권한 관계를 모르면 인가 결함을 완전히 판정할 수 없다.

## 4. WAF의 요청 처리 구조

WAF를 단순한 패턴 목록이 아니라 다음과 같은 처리 파이프라인으로 생각하면 이해하기 쉽다.

```text
HTTP 요청
   ↓
HTTP 파싱
   ↓
정규화
   ↓
변수 추출
   ↓
룰·문법 기반 검사
   ↓
정상 스펙과 비교
   ↓
세션·행위 문맥 결합
   ↓
허용 / 기록 / 차단
```

### HTTP 파싱

요청을 request line, header, cookie, query, body 등으로 분리하고 Content-Type에 맞는 parser를 적용한다.

예를 들어 body는 다음과 같이 서로 다른 구조를 가질 수 있다.

- `application/x-www-form-urlencoded`
- `multipart/form-data`
- `application/json`
- XML 계열 데이터

### 정규화

정규화의 목적은 공격자가 표현만 바꾸어 룰을 우회하는 것을 줄이는 것이다. URL decoding, Unicode 처리, path normalization 등 여러 변환이 여기에 포함될 수 있다.

하지만 "많이 정규화할수록 무조건 안전하다"고 보면 안 된다. **WAF가 해석한 최종 값과 백엔드가 해석한 최종 값이 같은가**가 더 중요하다.

## 5. 네거티브 모델과 포지티브 모델

### 네거티브 모델

이미 알고 있는 공격 특성을 찾는 방식이다.

예를 들어 SQL Injection이나 XSS의 특징을 특정 HTTP 변수에서 탐지한다. 여러 룰의 탐지 결과에 점수를 부여하고 임계값을 넘을 때 차단하는 anomaly scoring을 사용할 수도 있다.

장점은 기존 애플리케이션에 비교적 빠르게 적용할 수 있다는 것이다. 반면 알려지지 않은 공격이나 애플리케이션 고유의 비즈니스 로직 결함에는 한계가 있다.

### 포지티브 모델

"공격이 무엇인가"보다 **정상 요청이 무엇인가**를 먼저 정의한다.

개념적으로 다음과 같은 API 스펙이 있다고 하자.

```text
POST /profile

age
- integer
- 제한된 길이

email
- string
- 최대 길이 제한

정의되지 않은 필드
- 허용하지 않음
```

이 경우 알려진 공격 문자열이 없어도 스펙을 벗어나는 입력을 탐지할 수 있다.

정상 모델은 학습 트래픽으로 만들거나 OpenAPI 같은 API schema를 활용할 수 있다. 대신 애플리케이션 변경과 정상 동작의 다양성을 지속적으로 반영해야 하므로 운영 비용이 생긴다.

## 6. 문법 기반 탐지

정규식만으로 SQL이나 HTML/JavaScript의 모든 변형을 정확하게 구분하기 어렵다. 그래서 일부 탐지 엔진은 입력을 토큰이나 문법 구조로 해석한다.

중요한 사고방식은 다음과 같다.

```text
단순 패턴 탐지
"이 문자열이 있는가?"

구조 기반 탐지
"이 입력이 공격 언어의 유효한 구조를 이루는가?"
```

SQL Injection 탐지에서 토큰화·문법 기반 분석을 사용하면 단순 문자열 변형에 대한 저항력을 높일 수 있다. 다만 이것 역시 실제 애플리케이션의 쿼리 생성 방식과 권한 상태를 완전히 이해하는 것은 아니다.

## 7. 상태 기반 방어와 응답 검사

WAF 제품은 요청 하나만 독립적으로 보지 않고 세션이나 연속된 요청의 상태를 활용하는 기능을 제공할 수 있다.

예를 들어 제품과 구성에 따라 다음과 같은 보호 기능이 존재할 수 있다.

- cookie 무결성 보호
- hidden form field 변조 탐지
- CSRF 관련 보호
- 세션 단위 rate limiting
- 비정상적인 URL 흐름 탐지

중요한 것은 이런 기능이 **모든 WAF에 동일하게 존재하거나 항상 활성화된다고 일반화하지 않는 것**이다. 실제 점검에서는 제품 기능과 정책 설정을 확인해야 한다.

또한 일부 WAF는 서버 응답도 검사한다. 오류 메시지, stack trace, 민감정보 패턴 등 outbound data를 탐지하거나 마스킹하는 정책을 둘 수 있다.

이 관점은 웹 취약점 점검에도 연결된다.

> 요청 필터링만 보지 말고, 서버가 오류와 응답을 통해 어떤 정보를 외부로 내보내는지도 본다.

## 8. 봇·클라이언트 식별

현대의 웹 보안 제품은 요청 payload만으로 판단하지 않고 클라이언트의 특성이나 행동을 함께 평가하기도 한다.

예를 들어 JavaScript challenge, TLS fingerprint, browser fingerprint, 요청 빈도와 행동 패턴 등을 조합할 수 있다.

이 역시 WAF라는 제품군 전체의 필수 기능이라기보다 WAF·WAAP·bot management 제품에서 제공될 수 있는 확장 기능으로 보는 것이 안전하다.

## 9. WAF가 막기 어려운 영역

WAF가 HTTP를 깊게 이해한다고 해서 애플리케이션 취약점을 모두 차단할 수 있는 것은 아니다.

대표적인 예가 객체 수준 인가 결함이다.

```text
사용자 A → object 100 조회 : 허용
사용자 A → object 101 조회 : ?
```

두 번째 요청의 HTTP 문법과 parameter type이 완전히 정상이라면 WAF만으로 object 101이 사용자 A의 소유가 아니라는 사실을 알기 어렵다.

따라서 최종 인가 판단은 애플리케이션이 책임져야 한다.

이것은 중요한 방어 원칙으로 이어진다.

> WAF는 애플리케이션의 보안 코드를 대체하는 것이 아니라 추가 방어 계층이다.

## 10. IPS와 WAF의 배치와 역할 분담

개념적인 방어 계층은 다음처럼 그릴 수 있다.

```text
Internet
   ↓
Network access control
   ↓
IPS / network threat prevention
   ↓
WAF / web application protection
   ↓
Web Server / Application
```

실제 환경에서는 클라우드 서비스, CDN, load balancer, NGFW, WAF가 결합되거나 순서가 달라질 수 있으므로 이 그림을 고정된 물리 배치로 이해해서는 안 된다.

핵심은 역할이다.

| 관점 | IPS | WAF |
| --- | --- | --- |
| 주된 범위 | 여러 네트워크·애플리케이션 프로토콜 | HTTP/HTTPS 중심 |
| 분석 단위 | packet/flow/stream + protocol decoder | HTTP request/response의 구조화된 요소 |
| 강점 | 알려진 네트워크·프로토콜 공격을 넓게 탐지 | 웹 입력과 HTTP 문맥을 세밀하게 검사 |
| 대표 한계 | 앱 고유의 비즈니스 문맥 | 실제 애플리케이션 내부 인가 상태 |

둘은 대체재라기보다 서로 다른 공격면을 담당하는 방어 계층이다.

## 11. 취약점 분석과 연결되는 파서 정합성

이번 학습에서 가장 중요한 연결점은 **파서 정합성(parser consistency)** 이다.

최근 학습한 CVE-2026-85706에서도 앞단과 뒷단이 같은 URL을 다르게 해석하는 문제가 공격 체인의 한 축이었다.

```text
앞단 보안 계층의 해석
        ≠
백엔드 애플리케이션의 해석
        ↓
정책 우회 가능성
```

WAF 역시 같은 위험을 갖는다. WAF가 어떤 요청을 정상화한 결과와 WAS/framework가 실제로 해석한 결과가 다르면, WAF는 안전하다고 판단했지만 백엔드는 공격 의미로 해석하는 상태가 생길 수 있다.

따라서 보안 장비를 볼 때 "룰이 몇 개인가"보다 먼저 물어볼 질문이 있다.

> 이 장비의 HTTP parser와 보호 대상 애플리케이션의 parser는 경계 입력을 같은 의미로 해석하는가?

이 질문은 request smuggling, path normalization discrepancy, parser differential 같은 취약점 사고로 확장된다.

## 12. 공격자·방어자 관점

### 공격자 관점

WAF를 만났을 때 단순히 알려진 payload를 변형하는 것보다 다음 구조를 본다.

- WAF와 backend의 decoding 횟수가 같은가
- path normalization 순서가 같은가
- Content-Type별 parser가 같은 구조를 만드는가
- 중복 parameter를 어느 값으로 해석하는가
- header ambiguity를 서로 다르게 처리하는가
- 요청과 응답 사이에서 WAF가 유지하는 상태가 무엇인가

핵심은 **필터의 문자열 목록보다 해석기의 차이를 찾는 것**이다.

### 방어자 관점

방어자는 다음을 함께 관리해야 한다.

- HTTP parser와 normalization 정책
- backend와의 해석 정합성
- 네거티브 룰과 anomaly threshold
- API schema 기반 positive validation
- TLS inspection/termination 위치
- false positive와 예외 정책
- 응답 정보 노출 정책
- 애플리케이션 자체 인증·인가

WAF를 설치했다는 사실보다 **어떤 트래픽을 어떤 상태와 문맥으로 검사하도록 구성했는가**가 실제 보안 수준을 결정한다.

## 13. 현재 이해와 다음 검증 포인트

이번 학습에서 확보한 핵심 모델은 다음과 같다.

```text
IPS
= 여러 프로토콜을 넓게 관찰하고 공격 특성을 탐지하는 계층

WAF
= HTTP를 구조화해 파싱하고 정규화한 뒤
  변수·스키마·세션·행위 문맥을 이용해 웹 공격을 판정하는 계층
```

그리고 더 중요한 결론은 다음이다.

> WAF의 핵심은 단순한 시그니처 수가 아니라 HTTP를 어떻게 해석하고 백엔드와 같은 의미로 이해하느냐에 있다.

다음 단계에서는 허가된 테스트베드에서 동일한 HTTP 입력을 `proxy/WAF → backend` 양쪽에서 관찰하고, percent encoding·중복 parameter·Content-Type 변화 같은 경계 입력이 실제로 동일하게 해석되는지 검증해볼 수 있다. 그 결과가 쌓이면 현재 Log를 웹 방어 구조에 대한 Portfolio로 발전시킬 수 있다.
