# 서버 한 대에 IP가 여러 개인 이유 — ARP부터 로드밸런서까지

리눅스 서버에서 `ip addr show`를 실행하면 IP가 하나만 나오지 않는 경우가 많습니다. 어떤 서버는 `eth0`과 `eth1`에 각각 다른 대역의 주소가 붙어 있고, 어떤 서버는 `lo`에 `127.0.0.1`이 아닌 실제 서비스 주소가 걸려 있습니다. 심지어 **서로 다른 여러 서버가 완전히 같은 IP를 갖고 있는** 구성도 존재합니다.

마지막 경우는 처음 보면 설정 오류처럼 보입니다. 그러나 오류가 아니라 특정 부하분산 방식의 필수 조건입니다.

이 글은 그 이유를 IP 주소의 기초부터 순서대로 따라갑니다.

---

## 1. 준비 — IP와 네트워크 장비

### 1.1 IP 주소는 우편 주소처럼 읽는다

```
10.20.0  .  41
└─동네─┘   └집┘
```

앞부분이 **네트워크(대역)**, 뒷부분이 **호스트**입니다. 어디까지가 동네인지는 서브넷 마스크(`/24`, `/16` 등)가 정합니다.

`10.20.0.41`과 `10.20.0.42`는 같은 동네입니다. `10.20.0.41`과 `10.30.0.51`은 동네가 다르며, 서로 통신하려면 라우터를 거쳐야 합니다.

**이 대역 비교가 이후 모든 판단의 출발점입니다.** 한 서버에 IP가 두 개일 때, 대역이 같은지 다른지에 따라 해석이 완전히 갈립니다.

### 1.2 스위치·AP와 라우터는 다른 계층의 장비다

| 장비 | 계층 | 판단 기준 | IP 헤더 |
| --- | --- | --- | --- |
| 스위치, 무선 AP | 2계층 | MAC 주소 | 보지도 건드리지도 않음 |
| 라우터 | 3계층 | IP 주소 | 읽고 TTL을 1 감소 |

혼란의 원인은 가정용 "공유기"입니다. 그것은 **라우터 + 스위치 + 무선 AP를 한 상자에 넣은 물건**입니다.

### 1.3 "같은 대역이면 라우터를 거치지 않는다"의 의미

케이블 직결이라는 뜻이 아닙니다. **IP 계층에서 중간 경유지(hop)가 없다**는 뜻이며, 물리적으로는 당연히 스위치나 AP를 통과합니다.

> "라우터에 뭔가를 등록해야 그 IP로 트래픽이 온다"

**아닙니다.** 같은 대역 안에서는 라우터가 관여하지 않습니다. **서버 자신이 "그 IP는 내 것"이라고 ARP에 응답하면 그것만으로 트래픽이 옵니다.**

### 1.4 서브넷과 브로드캐스트 도메인은 다르다

| 용어 | 계층 | 정의 |
| --- | --- | --- |
| 서브넷 / 대역 | 3계층 | IP 주소의 논리적 묶음 |
| **브로드캐스트 도메인** | 2계층 | 브로드캐스트 프레임이 도달하는 범위 |

**ARP가 도달하는 범위는 3계층 서브넷이 아니라 2계층 브로드캐스트 도메인입니다.** 통상 1 VLAN = 1 브로드캐스트 도메인 = 1 서브넷으로 설계하므로 일치하지만, 하나의 VLAN에 서브넷 두 개를 얹으면(secondary subnet) 대역은 달라도 ARP는 서로에게 도달합니다.

브로드캐스트는 라우터를 통과하지 못합니다. **인터넷 연결 여부와 무관하며, 라우터를 하나라도 거치면 다른 세그먼트입니다.**

## 2. ARP — 주소의 주인을 정하는 방식

**"이 IP 주소를 가진 분, MAC 주소가 무엇입니까"라고 묻는 프로토콜입니다.** 자동으로 알려주는 방식이 아니라, 필요할 때 묻고 답하는 방식입니다.

```
PC(10.20.0.99)가 10.20.0.41로 보내려는 상황

① PC는 목적지 IP는 알지만 MAC을 모름.
② PC가 브로드캐스트로 "10.20.0.41 가지신 분?"이라고 질문.
③ 해당 서버가 자신의 MAC 주소를 유니캐스트로 응답.
④ PC가 결과를 ARP 테이블에 캐싱하고 이후 바로 전송.
```

**아무도 미리 알지 못합니다. 필요할 때 소리쳐 묻고, 대답하는 쪽이 주인입니다.**

> **"내가 그 IP의 주인이다"를 주장하는 행위가 곧 ARP 응답입니다.**

뒤에 나오는 "VIP를 광고한다"는 표현이 가리키는 것이 이것이고, "광고하지 마라"는 설정은 곧 "ARP에 응답하지 마라"는 뜻입니다. 또한 ARP 캐싱 때문에 잘못된 응답이 한 번 들어가면 캐시가 만료될 때까지 그 상태가 유지될 수 있으므로 설정 순서가 중요합니다.

## 3. IP를 추가하는 두 가지 방식

### 3.1 물리적으로 다른 망에 붙는다

서버 뒷면 랜선 구멍이 두 개이고 각각 다른 스위치에 연결됩니다. **현관문이 두 개인 집**입니다. 인증 서버처럼 서버망과 사무실망 양쪽에 있어야 하는 장비가 이렇게 구성됩니다.

### 3.2 소프트웨어로 주소만 추가한다

랜카드는 한 장인데 OS에 "이 주소도 내 것"이라고 등록만 합니다. **문패를 하나 더 다는 것**입니다.

| 상황 | 필요한 것 |
| --- | --- |
| 같은 대역에 IP 하나 더 | `ip addr add` 한 줄. 물리 경로는 이미 존재 |
| **다른 대역에 붙기** | **물리 경로 추가 필요** |

**IP 주소만 추가한다고 없던 길이 생기지 않습니다.**

### 3.3 loopback의 정확한 동작

문패를 거는 자리로 흔히 쓰이는 것이 **loopback(`lo`)** 이라는 가상 인터페이스입니다.

> **오해**: "패킷을 loopback으로 보내니 결국 자기가 받게 된다."

**결과는 맞지만 메커니즘이 틀렸습니다. "loopback으로 보낸다"는 전달 과정 자체가 없습니다.** 커널은 자기가 가진 모든 IP 주소의 목록을 유지하고, 패킷 목적지가 그 목록에 있으면 어느 인터페이스에 주소가 붙어 있든 로컬 수신으로 처리합니다.

**loopback은 리다이렉트 장치가 아니라, 케이블이 없어도 주소를 걸어둘 수 있는 옷걸이입니다.**

### 3.4 같은 IP를 한 서버에 중복 설정해도 되는가

**권장되지 않으며 실무상 금지 사항입니다.** 완전히 격리된 두 망에 동일 IP를 설정하는 것이 커널 차원에서 차단되지는 않으나, 동일 목적지에 대한 경로 선택이 모호해져 의도와 다른 인터페이스로 트래픽이 나갈 수 있습니다.

정상적인 "NIC 여러 장 + IP 하나" 구성은 본딩을 사용합니다.

## 4. 물리 경로를 늘리는 두 가지 방법

### 4.1 본딩 / 티밍 — 랜선은 여럿, IP는 하나

여러 물리 NIC을 하나의 논리 인터페이스로 묶습니다.

```
        bond0   10.20.0.61
       ┌───┴───┐
    eth0       eth1
      │          │
 [스위치 A]  [스위치 B]
```

| 모드 | 이름 | 동작 | 스위치 설정 |
| --- | --- | --- | --- |
| 1 | active-backup | 1가닥 사용, 나머지 대기, 장애 시 인계 | **불필요** |
| 4 | 802.3ad (LACP) | 전 가닥 동시 사용 | **필요 (LAG 구성)** |

- **active-backup**: 목적은 가용성이며 속도는 늘지 않습니다.
- **802.3ad**: 처리량을 높일 수 있으나 스위치와 서버 양쪽의 LACP 구성이 맞아야 합니다.

### 4.2 VLAN과 트렁크 포트 — 랜선은 하나, 대역은 여럿

**VLAN**은 스위치 한 대를 논리적으로 여러 대처럼 나누는 기술입니다. 여러 VLAN을 한 링크에 실어 나를 때 802.1Q 태그를 사용합니다.

#### 태그의 물리적 실체

프레임이 트렁크 포트로 나갈 때 **출발지 MAC 주소와 EtherType 사이에 4바이트 태그가 삽입**됩니다.

```
[일반]   목적지MAC | 출발지MAC |          EtherType | 데이터
[802.1Q] 목적지MAC | 출발지MAC | 태그(4) | EtherType | 데이터
```

- **TPID** `0x8100`: 태그 프레임 표시
- **PCP**: QoS 우선순위
- **VID**: 12비트. 일반적인 VLAN ID 사용 범위는 **1~4094**

#### Access와 Trunk

|  | Access 포트 | Trunk 포트 |
| --- | --- | --- |
| 연결 대상 | PC, 프린터 등 종단 | 스위치, 라우터, 방화벽, 하이퍼바이저, VLAN 인식 서버 |
| 수용 VLAN | 1개 | 여러 개 |
| 태그 | 없음 | 있음 |

서버를 트렁크 포트에 연결하면 **랜선 1가닥으로 여러 대역에 소속**될 수 있고, 서버에서는 `eth0.10`, `eth0.20` 같은 서브인터페이스로 나타납니다.

#### Native VLAN과 보안 관점

Native VLAN은 트렁크에서 태그 없이 처리되는 VLAN입니다. 양단의 native VLAN 불일치나 부적절한 trunk 협상은 VLAN 간 경계가 의도와 다르게 동작하게 만들 수 있습니다. 종단 포트는 명시적으로 access로 고정하고 불필요한 자동 trunk 협상을 비활성화하는 것이 중요합니다.

```
interface range FastEthernet0/1 - 20
 switchport mode access
 switchport access vlan 10
 switchport nonegotiate
```

정상적인 access 포트에서 종단 호스트가 태그된 프레임을 보내거나 스위치와 trunk를 협상하는 상황은 점검 대상입니다.

#### 용어 함정

"트렁크"는 문맥에 따라 **한 링크에 여러 VLAN을 싣는 VLAN trunk**와 **여러 물리 링크를 하나처럼 묶는 링크 집성**을 모두 가리킬 수 있습니다. 문서에서 용어를 만나면 어느 의미인지 먼저 확인해야 합니다.

## 5. 여러 서버가 같은 IP를 갖는 이유 — 부하분산

### 5.1 VIP는 서버의 주소가 아니라 서비스의 주소다

> **오해**: 로드밸런서가 뒷단 서버마다 가상 IP를 하나씩 나눠준다.
>
> **사실**: DR 구조에서는 VIP는 서비스 하나의 대표 주소이며, director와 real server들이 역할에 맞게 같은 VIP를 보유할 수 있다.

```
                        사용자 접속
                             │
                             ▼
                  ┌──────────────────────┐
                  │ lvs-01               │
                  │ NIC .0.11 · VIP .0.100│
                  └──────────┬───────────┘
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
       ┌────────────┐ ┌────────────┐ ┌────────────┐
       │ web-01     │ │ web-02     │ │ web-03     │
       │ NIC .0.41  │ │ NIC .0.42  │ │ NIC .0.43  │
       │ lo  .0.100 │ │ lo  .0.100 │ │ lo  .0.100 │
       └────────────┘ └────────────┘ └────────────┘
```

**"로드밸런서가 VIP를 물고 있다"**는 표현은 그 서비스 VIP로 들어오는 트래픽의 입구 역할을 한다는 뜻으로 이해할 수 있습니다.

### 5.2 LVS/IPVS 용어

| 용어 | 정체 | 위치 |
| --- | --- | --- |
| **LVS** | Linux Virtual Server 기술/프로젝트 | 개념 |
| **IPVS** (`ip_vs`) | 실제 부하분산을 수행하는 리눅스 커널 기능 | 커널 공간 |
| **ipvsadm** | IPVS 테이블 설정·조회 명령 | 사용자 공간 |
| **director** | IPVS가 동작하는 로드밸런서 노드 | 장비 |
| **real server** | 실제 요청을 처리하는 뒷단 서버 | 장비 |

### 5.3 세 가지 전달 방식

구분의 핵심은 **요청을 어떻게 real server에 전달하고 응답이 어떤 경로로 돌아오는가**입니다.

#### NAT — 목적지 IP를 바꿔 쓴다

LB가 요청의 목적지 주소를 real server 주소로 변환하고, 응답도 LB를 거쳐 반대 방향 변환을 거칩니다. 모든 응답이 director를 지나므로 director의 처리량 부담이 커질 수 있습니다.

#### DR (Direct Routing) — 목적지 MAC만 바꾼다

```
① 사용자 → LB      MAC: LB       | IP: 10.20.0.100
② LB가 MAC만 교체   MAC: web-01   | IP: 10.20.0.100
③ web-01 수신      MAC 일치 + lo에 .100 보유 → 처리
④ 응답             출발지 IP: 10.20.0.100 → 사용자에게 직행
```

IP를 손대지 않았으므로 응답은 director를 다시 통과할 필요가 없습니다. **이것이 여러 real server가 lo에 같은 VIP를 거는 이유입니다.**

DR은 L2 전달을 사용하므로 director와 real server가 같은 2계층 세그먼트에 있어야 하며, 서비스 포트도 동일하게 유지됩니다.

#### TUN — 원본 패킷을 한 번 더 감싼다

IP-in-IP 터널로 원본 패킷을 캡슐화해 전달하므로 DR의 동일 L2 세그먼트 제약을 완화합니다. 대신 캡슐화 오버헤드 때문에 MTU와 PMTU 문제를 점검해야 합니다. 작은 패킷은 정상인데 큰 전송에서만 멈추는 현상은 이런 문제의 중요한 단서가 될 수 있습니다.

|  | NAT | DR | TUN |
| --- | --- | --- | --- |
| 바꾸는 것 | 목적지 IP 변환 | 목적지 MAC | 외부 IP 헤더 추가 |
| 응답 경로 | LB 경유 | 직행 | 직행 |
| real server 추가 설정 | 상대적으로 적음 | lo VIP + ARP 제어 | 터널 인터페이스 |
| 망 제약 | 구성에 따라 LB를 경로에 포함 | 동일 L2 세그먼트 | 원격 배치 가능 |
| LB 데이터 경로 부담 | 요청+응답 | 주로 요청 | 주로 요청 |

### 5.4 DR의 필수 조건 — 갖고 있되 말하지 마라

VIP를 lo에 걸어둔 real server가 같은 네트워크의 VIP ARP 질의에 경쟁적으로 응답하면 클라이언트가 director 대신 real server의 MAC을 학습할 수 있고, 결과적으로 부하분산 경로가 무력화될 수 있습니다.

- **`arp_ignore`** — 어떤 조건에서 ARP 요청에 응답할지 제한합니다. DR에서는 lo의 VIP에 대한 요청이 물리 NIC로 들어왔을 때 real server가 응답하지 않도록 구성하는 데 사용합니다.
- **`arp_announce`** — 호스트가 ARP를 보낼 때 부적절한 로컬 주소를 출발지로 선택해 이웃의 ARP 캐시를 혼란시키는 일을 줄이는 데 사용합니다.

> **주의**: lo에 VIP를 올렸다는 사실만으로 ARP가 자동 억제되는 것은 아닙니다. 실제 sysctl 설정을 함께 확인해야 합니다.

### 5.5 director는 어떻게 서버를 고르는가

가상 서비스는 **VIP:포트** 단위로 식별합니다. 신규 연결은 rr(round-robin), wrr(weighted round-robin), lc(least-connection) 등의 스케줄링 정책으로 real server를 선택하고, 같은 연결의 후속 패킷은 해당 연결 상태에 따라 같은 real server로 전달됩니다.

**"맞는 서버"는 미리 정해진 한 대가 아니라 스케줄링 결과입니다.** 따라서 클러스터의 어느 정상 real server가 선택되어도 서비스 결과가 일관되어야 합니다.

### 5.6 응답이 director를 거치지 않으면 왜 부담이 주는가

| 구분 | NAT | DR |
| --- | --- | --- |
| 요청 경로 | 클라이언트 → LB → 서버 | 클라이언트 → LB → 서버 |
| 응답 경로 | 서버 → **LB** → 클라이언트 | 서버 → 클라이언트 (직행) |
| LB 데이터 경로 | 요청 + 응답 | **주로 요청** |

웹 서비스는 작은 요청에 비해 응답 데이터가 훨씬 큰 경우가 많습니다. DR에서 응답을 직접 보내면 director가 큰 응답 트래픽을 처리하지 않아도 되므로 데이터 경로 부담을 줄일 수 있습니다. 이 구조는 **비대칭 경로(asymmetric path)** 로 이해하는 편이 정확합니다.

### 5.7 L7 프록시는 규칙이 다르다

L7 프록시는 클라이언트 연결을 프록시에서 종료하고 real server와 별도 연결을 만듭니다. 따라서 DR처럼 real server의 lo에 서비스 VIP를 복제해야 하는 구조가 아닙니다.

**따라서 "lo에 VIP가 없다 = 부하분산 대상이 아니다"는 성립하지 않습니다.** lo VIP는 부하분산 일반의 표지가 아니라 DR 구조를 판별할 때의 단서입니다.

### 5.8 로드밸런서는 강제 통로가 아니다

DR 구조에서도 real server의 실제 주소가 네트워크에서 직접 도달 가능하다면 사용자가 LB를 거치지 않고 real server에 접근할 수 있습니다. **주소를 모르게 하는 것은 접근 통제가 아닙니다.**

보안 점검에서는 다음을 함께 봐야 합니다.

- real server의 서비스 포트가 불필요하게 사용자 망에 직접 노출되는가
- LB/WAF/필터링/레이트리밋을 real IP 직접 접속으로 우회할 수 있는가
- 응답 헤더·에러 페이지·DNS 이력·인증서 등에서 real IP가 노출되는가
- 클러스터 노드 간 패치 수준과 정책이 일관적인가

설계 원칙은 **사용자는 VIP로 진입하고, real server의 직접 서비스 경로는 필요한 소스에만 허용**하는 것입니다.

## 6. 또 하나의 "같은 IP" — 이중화 부동 주소

로드밸런서 자체의 단일 장애점을 줄이기 위해 서비스 주소를 두 노드 중 활성 노드가 보유하도록 구성할 수 있습니다.

```
평상시              장애 후
lb01 ★ .200 보유    lb01 (다운)
lb02   (대기)       lb02 ★ .200 인수
```

이 구조에서 **VRRP**는 가상 라우터 이중화를 위한 프로토콜이고 **keepalived**는 리눅스에서 VRRP 등을 구현하는 데 널리 쓰이는 소프트웨어입니다. MASTER의 광고가 일정 시간 사라지면 BACKUP이 MASTER 역할과 가상 주소를 인수합니다.

핵심은 **"죽었다는 신호"를 받는 것이 아니라 정상 광고가 끊긴 것을 보고 장애를 판단한다**는 점입니다.

---

## 7. 정리 — 같은 IP가 여러 곳에 보이는 경우

| 유형 | 주소의 역할 | 주소 보유 형태 | ARP 관점 |
| --- | --- | --- | --- |
| **서비스 VIP** | 서비스 대표 주소 | 활성 director/LB가 서비스 진입점 역할 | 서비스 진입점이 응답 |
| **DR의 lo VIP** | real server의 로컬 수신용 VIP | DR 대상 real server들이 같은 VIP 보유 | real server의 VIP 응답 억제 필요 |
| **VRRP 부동 주소** | HA용 이동 서비스 주소 | 정상적으로는 현재 MASTER가 활성 보유 | 현재 MASTER가 응답 |

두 번째와 세 번째는 겉보기가 비슷하지만 의미가 다릅니다. DR의 lo VIP는 패킷을 로컬 처리하기 위한 복제 주소이고, VRRP 주소는 장애 시 활성 노드가 바뀌는 부동 주소입니다.

## 8. 한 서버에 IP가 둘일 때 — 대역별 판별

### 8.1 대역이 다른 경우

```
10.20.0.51 / 10.30.0.51
```

서버가 여러 네트워크에 연결된 이유를 NIC, VLAN, 본딩 조합 관점에서 확인합니다.

| 방법 | 물리 링크 | 확인 단서 |
| --- | --- | --- |
| NIC 여러 장 | 여러 링크 | `ip -d link show`의 물리 인터페이스 |
| VLAN 태깅 | 한 링크에서도 가능 | `eth0.10`, `eth0.20` 같은 VLAN 인터페이스 |
| 본딩 + VLAN | 여러 링크 | `bond0.10`, `bond0.20` 등 |

### 8.2 대역이 같은 경우

**① Secondary IP** — 한 인터페이스/네트워크에 주소를 추가한 경우.

**② 클러스터·이중화 부동 주소** — 노드 고유 주소와 이동 가능한 서비스 주소가 함께 있는 경우.

**③ 여러 NIC가 같은 대역에 연결** — 가능하지만 라우팅·ARP 동작을 명확히 설계해야 하며, 링크 이중화 목적이라면 보통 본딩 같은 논리 인터페이스를 사용합니다.

### 8.3 lo에 `127.0.0.1`이 아닌 주소가 있는 경우

DR 방식 부하분산의 real server인지 의심할 수 있습니다. 단, 이것만으로 확정하지 말고 다음을 함께 확인합니다.

```bash
ip addr show
ip -d link show
ip route show
sysctl -a | grep arp_ignore
ipvsadm -Ln
cat /proc/net/ip_vs
```

## 9. 기존 인프라 자산과 연결 — 자산 계층화 점검 순서

기존 `asset-layering-01`에서 정리한 **물리 → OS → 상위 SW** 점검 원칙에 이 네트워크 판별을 결합하면, 서버의 IP 구성을 다음 순서로 해석할 수 있습니다.

1. **물리/논리 인터페이스 식별** — NIC, bond, VLAN 서브인터페이스를 구분한다.
2. **주소와 경로 확인** — NIC IP, secondary IP, lo VIP, 라우팅 테이블을 확인한다.
3. **ARP 동작 확인** — VIP가 있다면 누가 응답해야 하는 구조인지와 `arp_ignore` 등 억제 설정을 확인한다.
4. **상위 네트워크 기능 확인** — IPVS/LVS, keepalived/VRRP, L7 프록시 등 서비스 구조를 확인한다.
5. **보안 경계 확인** — VIP 우회, real IP 직접 접근, VLAN/trunk 오구성, 정책·패치 편차를 점검한다.

즉 **IP가 여러 개라는 현상만 보고 취약점이나 오류로 판단하지 않고, 그 주소가 어느 계층에서 어떤 역할을 하는지 먼저 식별**해야 합니다. 이 순서는 기존 자산 계층화 원칙의 네트워크 확장판입니다.

## 10. 헷갈리기 쉬운 용어 정리

| 단어 | 의미 1 | 의미 2 |
| --- | --- | --- |
| **트렁크** | VLAN 다중화 | 링크 집성 의미로 쓰이는 벤더 용어 |
| **가상 IP** | 서비스 VIP | VRRP 부동 주소, secondary IP 등 문맥별 의미 |
| **본딩 / 티밍** | 여러 NIC를 논리 링크로 묶는 계열 기술 | OS·구현에 따라 명칭과 기능 차이 존재 |
| **loopback** | `127.0.0.1` 계열의 로컬 주소 | 서비스 주소를 안정적으로 붙여 두는 가상 인터페이스 |
| **우회** | 의도하지 않은 보안 경로 | DR의 정상적인 비대칭 응답 경로를 설명할 때 쓰이는 상대적 표현 |

개념 수준에서는 특히 다음을 분리합니다.

| 구분해야 할 것 | 차이 |
| --- | --- |
| 서브넷 vs 브로드캐스트 도메인 | 3계층 논리 묶음 vs 2계층 도달 범위 |
| ARP 수신 vs ARP 응답 | `arp_ignore`는 응답 정책이며 IP 패킷 수신 여부와 같은 개념이 아님 |
| 정보 은닉 vs 접근 통제 | 주소를 모르는 것과 네트워크 정책으로 접근을 차단한 것은 다름 |

## 11. 한 문장 요약

**IP는 서버의 신분증 하나가 아니라 인터페이스와 서비스 구조에 따라 여러 역할로 배치되는 주소입니다.** 여러 IP나 여러 서버의 동일 IP를 발견했을 때는 ARP, L2/L3 경로, loopback, 부하분산, 이중화의 순서로 역할을 판별해야 합니다.
