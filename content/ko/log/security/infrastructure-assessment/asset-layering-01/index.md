## 핵심 기준

분류가 헷갈릴 때 던질 질문은 하나다.

> **이 계층의 셸(또는 설정 파일)에 접근할 수 있는가?**

접근할 수 있으면 우리 점검 범위다. 접근할 수 없으면 해당 제품의 관리 인터페이스로 점검하고, 나머지는 `N/A + 사유`를 남긴다.

| 자산 | OS 점검 | 상위 소프트웨어 점검 | 근거 |
| --- | --- | --- | --- |
| 물리 서버 | O | O | 전부 자체 운영 |
| 하이퍼바이저 위 VM | O | O | 하이퍼바이저는 별도 점검 |
| IaaS 인스턴스 | O | O | 클라우드 계정은 별도 점검 |
| 쿠버네티스 노드 | O | O | 클러스터는 별도 점검 |
| 온프레미스 형상관리 서버 | O | O | OS + 웹서버 + DB + 앱 4계층 |
| 소프트웨어형 보안솔루션 | **O** | O | 범용 OS 위 설치 |
| 보안 어플라이언스 | X | O | 셸 접근 불가 |
| 관리형 DB | X | 일부 | 파라미터·계정만 점검 가능 |
| SaaS | X | 설정 화면만 | 전 계층 제공자 책임 |
| 서버리스/PaaS | X | 클라우드 분야로 점검 | OS 개념 없음 |

## 가상화 — ESXi와 vCenter

ESXi는 애플리케이션이 아니라 **OS 그 자체**다. 물리 서버에 Windows나 Linux 대신 설치되며, 하드웨어 자원을 나눠 VM에 제공한다. 그 위에 Ubuntu 같은 게스트 OS를 올리면 게스트 OS는 자신이 물리 서버인지 VM인지 구분하지 못한다.

vCenter는 여러 ESXi를 중앙에서 관리하는 서버이며 vMotion, HA, DRS 같은 기능을 제공한다.

### vCenter만 점검하면 안 되는 이유

1. ESXi 개별 설정인 SSH 활성화, Lockdown Mode, 셸 타임아웃 등을 vCenter가 전부 보여주지 않는다.
2. vCenter에 등록되지 않은 standalone ESXi는 아예 보이지 않는다.
3. vCenter 자체가 전 인프라에 대한 고권한 관리 시스템이므로 별도 점검 대상이다.

따라서 **vCenter는 점검을 효율화하는 창구이지 ESXi 점검의 대체 수단이 아니다.** PowerCLI로 설정을 일괄 수집하는 것은 유효하지만, 점검 대상은 여전히 ESXi 전수다.

버전 호환성도 주의해야 한다. **vCenter는 자신보다 상위 버전의 ESXi를 관리할 수 없다.** 예를 들어 vCenter 7.0만 있는데 ESXi 8.0이 섞여 있다면 해당 호스트는 미등록 상태일 가능성이 있다.

또한 **vCenter는 게스트 OS 내부 설정을 볼 수 없다.** VM은 vCenter 입장에서는 내용물을 알 수 없는 검은 상자이며, 게스트 OS 점검은 각 VM에 SSH 등으로 접속해 물리 서버와 동일한 방식으로 수행한다.

## 쿠버네티스

쿠버네티스는 별도 하드웨어나 가상화 계층이 아니라 **OS 위에서 동작하는 여러 데몬과 구성요소의 집합**이다. control-plane 노드와 worker 노드는 역할과 설치 구성요소가 다를 뿐 하드웨어와 OS 자체는 동일한 기반을 사용할 수 있다.

| 노드 | 주요 구성요소 |
| --- | --- |
| control-plane | kube-apiserver, etcd, scheduler, controller-manager, kubelet, containerd |
| worker | kubelet, kube-proxy, containerd |

가상화가 서버 한 대의 자원을 여러 VM으로 쪼개는 기술이라면, 쿠버네티스는 **여러 서버를 하나의 자원 풀처럼 사용하도록 묶는 기술**이다. 온프레미스에서는 하이퍼바이저 위에 VM을 만들고 그 VM들을 쿠버네티스 클러스터로 묶는 식으로 두 계층이 함께 존재할 수 있다.

### 배포 흐름

1. 개발자가 `kubectl apply`로 원하는 애플리케이션 상태를 선언한다.
2. 요청이 사용 가능한 control-plane 엔드포인트로 전달된다.
3. kube-apiserver가 인증·인가 후 상태를 etcd에 저장한다.
4. scheduler가 적절한 worker 노드를 선택한다.
5. 해당 노드의 kubelet이 컨테이너 런타임에 실행을 지시한다.

노드가 장애를 일으키면 controller-manager 등이 상태를 감지하고 다른 노드에 워크로드가 다시 배치될 수 있다.

### 점검 단위

| 항목 성격 | 단위 | 예시 |
| --- | --- | --- |
| 클러스터 전체 설정 | 클러스터당 1회 | RBAC, NetworkPolicy, Pod Security, 감사 로그 |
| 노드별 설정 파일 | 노드마다 | kubelet 설정, 인증서 파일 권한 |

CIS Kubernetes Benchmark는 control-plane과 worker, 정책 항목을 구분해 다룬다. 따라서 **control-plane 노드만 확인해서는 안 된다.** `kube-bench` 같은 도구는 실행 위치의 역할에 맞춰 관련 항목을 점검하는 데 활용할 수 있다.

### 노드 OS 점검만으로 잡히지 않는 항목

- **NetworkPolicy 미적용**: 네트워크 정책이 없으면 Pod 간 통신이 과도하게 허용될 수 있다. 이 문제는 일반적인 OS 방화벽 점검만으로 충분히 드러나지 않는다.
- **etcd 데이터 암호화 미적용**: Secret 등 민감 데이터가 저장 시 암호화되지 않을 수 있다. 파일 권한이 적절해도 데이터 보호 수준은 별도 확인이 필요하다.
- **privileged 컨테이너**: 과도한 권한의 컨테이너는 호스트 자원에 광범위하게 접근할 수 있어, 노드 OS 설정이 정상이어도 격리 경계를 약화시킬 수 있다.

관리형 서비스인 EKS, AKS, GKE에서는 control plane 일부가 클라우드 제공자 책임이다. 따라서 자체 구축 환경과 관리형 환경은 **동일한 점검표를 그대로 쓰지 말고 적용 가능 항목과 N/A 항목을 분리**해야 오탐을 줄일 수 있다.

## SaaS와 관리형 서비스의 차이

| 구분 | SaaS | 관리형(PaaS) | IaaS |
| --- | --- | --- | --- |
| 예시 | 형상관리 SaaS, 그룹웨어 | 관리형 DB, 캐시 | VM 인스턴스 |
| 하드웨어·OS | 제공자 | 제공자 | 제공자 |
| 엔진 | 제공자 | 제공자 운영 / **우리가 설정** | 우리 |
| 우리가 만질 수 있는 것 | 설정 화면 | **파라미터, 계정, 네트워크** | 전부 |
| 전통적 서버 점검 항목 적용률 | 해당 없음 | 일부 적용 | 대부분 적용 |

관리형 DB는 **OS는 볼 수 없지만 DB 자체 설정은 상당 부분 확인할 수 있는 중간 지대**다. 엔진 버전, 파라미터, 계정, 네트워크 설정은 사용자가 선택하거나 관리할 수 있지만 SSH로 호스트 OS에 들어갈 수는 없다.

따라서 관리형 서비스 점검에서는 **적용 가능 항목과 N/A 항목을 사전에 매핑한 표를 만들어 두는 것**이 중요하다. 이는 실제 점검 범위를 명확히 하고 심사·감사 대응 시 책임 경계를 설명하는 근거가 된다.

## 정리

계층별 점검 범위는 제품 이름보다 **접근 가능한 관리 경계**를 기준으로 판단한다.

- 셸이나 설정 파일에 접근할 수 있으면 해당 계층은 직접 점검 대상이다.
- 관리 인터페이스만 제공되면 그 인터페이스에서 확인 가능한 설정만 점검한다.
- 접근할 수 없는 하위 계층은 `N/A` 처리하고 사유와 책임 주체를 남긴다.
- 가상화, 쿠버네티스, 관리형 서비스처럼 계층이 겹치는 환경에서는 OS·하이퍼바이저·클러스터·관리 서비스 설정을 서로 다른 점검 단위로 분리한다.
