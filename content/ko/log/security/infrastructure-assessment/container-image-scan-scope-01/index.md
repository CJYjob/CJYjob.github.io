## 문제: 무엇을 이미지 점검 대상으로 볼 것인가

컨테이너 환경의 취약점 점검을 준비하면서 먼저 부딪힌 문제는 도구 선택보다 **대상 범위**였다. 레지스트리에는 표준으로 관리하는 이미지, 외부에서 가져온 기반 이미지, 배포 과정에서 생성되는 이미지가 함께 있을 수 있다. 이들을 모두 같은 책임 범위로 보고 스캔하면 결과의 소유자와 조치 주체가 불명확해진다.

작업에서는 관리 주체와 사용 목적을 확인해 점검할 이미지 범위를 먼저 정했다. 범위 밖의 이미지가 안전하다는 뜻은 아니다. 이번 점검의 대상으로 합의되지 않았다는 뜻이며, 별도 관리가 필요하다면 그 결정을 따로 기록해야 한다. 고객별 이미지 이름과 레지스트리 구성은 이 글에서 다루지 않는다.

## 접근 권한과 실행 환경

점검자에게는 필요한 범위의 읽기 권한을 요청했다. 이미지와 메타데이터를 확인하는 일, 스캔 기능을 활성화하거나 설정을 변경하는 일은 권한과 책임이 다르다. 그래서 어떤 값은 점검자가 조회하고, 어떤 설정은 운영 담당자가 확인·변경할지 구분했다.

로컬 점검 단말에서는 명령줄 도구의 TLS 연결이 정상적으로 동작하지 않았다. 인증서 신뢰 설정을 반복하는 것만으로 해결되지 않아 접속 경로와 실행 환경을 분리해 보았다. 결국 허용된 클라우드 셸 환경에서 읽기 전용으로 레지스트리 목록을 확인하고 이미지 점검을 실행했다. 임시 셸은 세션이 끝나면 작업 파일이 남지 않을 수 있으므로, 명령 실행 성공과 결과 보존을 별개 작업으로 다뤄야 한다는 점도 확인했다.

## Trivy 실행에서 확인한 것

범위에 포함된 표준 이미지 일부를 고정된 이미지 식별자로 선택해 Trivy 점검을 수행했다. 도구가 출력한 취약점 건수만으로 조치 결론을 내리지는 않았다. 동일한 기반 이미지에서 결과가 반복될 수 있고, 실제 조치 방향은 이미지 갱신 주기와 해당 이미지의 관리 책임에 영향을 받기 때문이다.

여기까지 확인한 것은 **선정한 이미지에 대한 점검 실행과 결과 해석의 출발점**이다. 전체 이미지 점검 완료, 조치 가능 건수 산출, 모든 결과 파일의 보존까지 마쳤다는 의미는 아니다. 다른 클라우드의 레지스트리 스캔은 당시 계획과 권한 협의 단계였으므로 완료된 작업으로 적지 않는다.

## OS 점검과 이미지 점검의 관계

운영 형태에 따라 호스트 OS에 직접 접근하지 못할 수 있다. 이때 기존 서버 점검 스크립트를 그대로 적용해 빈 결과를 얻는 대신, 관리 가능한 계층을 구분해야 한다. 이미지 점검은 이미지에 포함된 구성요소와 알려진 취약점을 살펴보는 경로다. 실행 중 설정, 권한, 네트워크 노출 등은 별도의 점검이 필요할 수 있다. 따라서 이미지 스캔 한 번으로 컨테이너 환경의 모든 보안 항목을 확인했다고 결론 내릴 수 없다.

## 다음에 같은 일을 한다면

점검을 시작하기 전에 다음 네 가지를 먼저 문서화하겠다.

1. 점검할 이미지의 선정 기준과 관리 주체
2. 사용할 권한과 설정 변경 담당자
3. 실행 환경 및 결과 파일 보존 방법
4. 이미지 점검으로 확인되는 항목과 별도 확인이 필요한 항목

도구 실행보다 범위와 책임을 먼저 정해야 결과를 실제 조치 계획으로 연결할 수 있었다.
